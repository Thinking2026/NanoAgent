## 1. 为什么要造这个轮子

市面上已经有 LangChain、AutoGen、CrewAI 等成熟框架，为什么还要从头构建一个 Agent 框架？

答案是：**现有框架在生产可靠性上的设计不够深入**。

大多数框架解决了"让 Agent 能跑起来"的问题，但在以下场景下表现不佳：

- **长任务中途崩溃**：没有检查点机制，几小时的任务从头重来
- **LLM 提供商不稳定**：单一提供商故障导致整个任务失败
- **上下文窗口溢出**：任务越复杂，越容易撞上 token 上限
- **工具调用死循环**：LLM 反复调用同一工具却没有进展
- **结果质量无保障**：Agent 给出答案但没有验证机制

这些问题在 demo 环境下几乎不会出现，但在生产环境中会频繁发生。一个需要调用 20 次工具、跨越 5 个步骤的复杂任务，在执行过程中遇到任何一个问题都可能导致整个任务失败。

### 1.1 现有框架的设计局限

以 LangChain 为例，它提供了丰富的组件和集成，但核心的执行循环相对简单：调用 LLM，解析工具调用，执行工具，把结果放回上下文，循环。当这个循环出错时，通常的处理方式是抛出异常，让调用方决定怎么办。

这种设计在简单场景下没问题，但对于复杂的多步骤任务，你需要更精细的控制：

- 这次失败是暂时的网络问题，还是计划本身有缺陷？
- 应该重试当前步骤，还是重新规划后续所有步骤？
- 如果 LLM 提供商挂了，能不能无缝切换到备用提供商？
- 任务执行了 2 小时后崩溃，能不能从第 8 步继续而不是从头来？

这些问题需要在框架层面系统性地解决，而不是让每个应用开发者自己实现。

### 1.2 NanoAgent 的设计哲学

NanoAgent 的设计目标是：**在保持代码简洁的前提下，把这些生产级问题都解决掉**。

"轻量级"不意味着功能简陋，而是意味着每一行代码都有明确的目的，没有不必要的抽象和过度设计。整个框架的核心设计理念可以用一句话概括：

**每一个可能失败的地方，都要有对应的恢复策略；每一个恢复策略，都要有代价意识。**

这句话包含两个关键点：

第一，"每一个可能失败的地方"——这要求在设计阶段就系统性地思考所有可能的失败模式，而不是等到出问题了再打补丁。

第二，"代价意识"——不是所有失败都需要最激进的恢复策略。如果只是工具参数写错了，重试一次就够了，没必要重新生成整个计划。代价意识让系统在可靠性和效率之间找到平衡。

### 1.3 技术选型的考量

在技术选型上，NanoAgent 做了几个刻意的选择：

**Python 3.13+ 和全量类型注解**：类型注解不只是文档，它让 IDE 能够提供准确的代码补全和错误检查，大幅降低了维护成本。在一个有几十个模块的框架中，类型安全尤为重要。

**HTTP REST 直接对接各提供商 API**：没有使用 OpenAI SDK 或 Anthropic SDK，而是直接用 HTTP 客户端。这样做的好处是：对每个提供商的请求/响应格式有完全的控制权，可以精确处理各种边缘情况（比如不同提供商的 Retry-After 头格式不同）。

**SQLite 作为默认存储**：零依赖，开箱即用。对于大多数使用场景，SQLite 的性能完全够用。需要更高性能时，可以切换到 MySQL 或 ChromaDB，存储接口是抽象的。

**Jinja2 模板引擎管理提示词**：把提示词从代码中分离出来，放到模板文件里。这让提示词的修改不需要改代码，也让提示词的版本管理更清晰。

## 2. 整体架构：五层分离的设计哲学

### 2.1 分层架构

NanoAgent 采用严格的五层垂直分离架构：

```
┌─────────────────────────────────────────────────────────────┐
│                      应用入口层 (Entry)                       │
│              main.py  →  Demo  →  PipelineThread             │
├─────────────────────────────────────────────────────────────┤
│                    应用编排层 (Application)                   │
│         Pipeline  ←→  PipelineDriver  ←→  AgentFactory       │
├─────────────────────────────────────────────────────────────┤
│                    Agent 模型层 (Models)                      │
│  Analyzer │ Planner │ StageExecutor │ ReasoningManager       │
│  ContextManager │ ModelSelector │ QualityEvaluator           │
│  CheckpointManager │ KnowledgeManager │ PersonalityManager   │
├─────────────────────────────────────────────────────────────┤
│                    基础能力层 (Infrastructure)                │
│   LLMGateway │ ToolRegistry │ Storage │ Tracer │ EventBus    │
├─────────────────────────────────────────────────────────────┤
│                    基础设施层 (Infra)                         │
│   SQLite/ChromaDB/MySQL │ Jinja2 │ HTTP Client │ Logger      │
└─────────────────────────────────────────────────────────────┘
```

### 2.2 为什么这样分层？

**分层的本质是控制变化的传播范围**。

软件系统中，变化是不可避免的。LLM 提供商会更新 API，存储需求会变化，推理策略会迭代。分层架构的价值在于：当某一层发生变化时，影响范围被限制在该层内部，不会向上或向下传播。

具体来说：

- 当你需要把 SQLite 换成 PostgreSQL 时，只需要改基础设施层，上面四层完全不感知
- 当你需要把 ReAct 换成 Tree-of-Thought 推理策略时，只需要替换 Agent 模型层的 Strategy 实现，其他层不受影响
- 当你需要添加新的 LLM 提供商时，只需要在基础能力层添加一个新的 Client 实现，上层代码不需要修改

这种分层还带来了一个重要的副作用：**每一层都可以独立测试**。你可以用 mock 的 LLMGateway 测试 Pipeline 的编排逻辑，而不需要真正调用 LLM API。你可以用 mock 的 ToolRegistry 测试 StageExecutor 的推理循环，而不需要真正执行工具。

### 2.3 Pipeline 是唯一的"上帝视角"

在 Agent 模型层，有一个特殊的角色：`Pipeline`。它是整个系统中唯一持有所有核心组件引用的类，负责协调各模块按正确顺序工作。

这是一个刻意的设计决策。我们没有让各模块互相持有引用（那会形成复杂的依赖网），而是让 Pipeline 作为中央协调者，所有模块只向 Pipeline 汇报，Pipeline 决定下一步调用谁。

想象一下如果不这样设计会发生什么：Planner 需要持有 QualityEvaluator 的引用（因为计划生成后需要评审），StageExecutor 需要持有 Planner 的引用（因为阶段失败后需要重规划），QualityEvaluator 需要持有 LLMGateway 的引用（因为评估需要调用 LLM）。这些交叉引用会形成一张复杂的依赖网，任何一个模块的修改都可能影响多个其他模块。

Pipeline 的"星形拓扑"依赖关系解决了这个问题：**你只需要读懂 Pipeline，就能理解整个任务的执行逻辑**。所有的协调逻辑都集中在一个地方，而不是分散在各个模块中。

### 2.4 AgentFactory：依赖注入的统一入口

所有组件通过 `AgentFactory` 统一构建，这不只是为了代码整洁，更重要的是：

**测试替换**：测试时可以注入 mock 组件，不需要修改业务代码。比如，测试 Pipeline 的恢复逻辑时，可以注入一个总是返回失败的 mock QualityEvaluator，而不需要真正调用 LLM。

**配置集中**：所有组件的配置参数从同一个 `ConfigReader` 读取。这意味着你只需要修改一个配置文件，就能调整整个系统的行为，而不是在代码的各个角落寻找硬编码的参数。

**依赖可见**：组件的依赖关系在 Factory 中一目了然，不会出现隐式依赖。当你看到 `build_stage_executor()` 需要传入 `reasoning_manager`、`context_manager`、`quality_evaluator` 等参数时，你立刻就知道 StageExecutor 依赖哪些组件。

**生命周期管理**：Factory 控制组件的创建顺序，确保依赖关系正确初始化。比如，LLMGateway 必须在 ReasoningManager 之前创建，因为 ReasoningManager 依赖 LLMGateway。

### 2.5 PipelineDriver：用户与 Agent 的消息桥梁

`PipelineDriver` 是一个容易被忽视但非常重要的设计。它解决了一个并发问题：**用户可能在任务执行过程中发送指令（取消、引导、澄清），而 Agent 正在另一个线程中执行任务**。

PipelineDriver 使用线程安全的消息队列作为桥梁：

- 用户线程：通过 `submit_task()`、`send_cancel()`、`send_guidance()` 等方法向队列写入指令
- Agent 线程：在每次推理迭代开始时，通过 `loop_user_messages(timeout)` 非阻塞地轮询队列

这种设计的优雅之处在于：Agent 不需要主动等待用户指令，而是在自然的循环间隙检查是否有新指令。用户也不需要等待 Agent 完成当前操作才能发送指令。

### 2.6 事件总线：解耦通知

跨模块的状态通知通过 `EventBus` 发布，而不是直接调用。这意味着：

- `StageExecutor` 不需要知道谁在监听阶段完成事件
- 前端 UI、监控系统、审计日志可以独立订阅感兴趣的事件
- 添加新的监听者不需要修改任何现有代码

系统定义了 15+ 个领域事件，覆盖从任务分析开始到最终交付的完整生命周期：`TaskAnalysisStarted`、`PlanGenerateSucceed`、`StageExecutionStarted`、`ToolCallStarted`、`ToolCallResultProduced`、`TaskExecutionSucceed` 等。

这些事件不只是用于通知，它们也是系统状态的完整记录。通过订阅所有事件，你可以重建任务执行的完整时间线，这对于调试和审计非常有价值。

### 2.7 不可变领域对象：防御性设计

核心领域对象（`Task`、`Plan`、`PlanStep`）使用 `@dataclass(frozen=True)` 声明为不可变。这是一个防御性设计决策。

在多线程环境中，可变的共享状态是 bug 的温床。如果 `Task` 对象是可变的，那么在 Pipeline 读取 `task.task_goal` 的同时，另一个线程可能正在修改它，导致难以复现的竞态条件。

不可变对象从根本上消除了这类问题：一旦创建，对象的状态就不会改变。需要"修改"时，创建一个新对象。这种模式在函数式编程中很常见，在并发场景下尤为有价值。

## 3. 三级循环：Agent 可靠性的核心机制

这是 NanoAgent 最核心的设计，也是它与大多数 Agent 框架最大的区别。

### 3.1 问题的本质

LLM Agent 执行复杂任务时，失败是常态，不是异常。工具调用可能失败，LLM 可能给出错误的推理，计划可能不合理，提供商可能不稳定。

**关键问题不是"如何避免失败"，而是"失败后如何以最小代价恢复"**。

这个认知转变非常重要。如果你把精力放在"避免失败"上，你会发现这是一场无休止的战争——总有新的失败模式出现。但如果你把精力放在"优雅地从失败中恢复"上，你会发现系统的可靠性可以系统性地提升。

### 3.2 三级嵌套循环

NanoAgent 设计了三级嵌套的执行循环，每一级都有独立的失败检测和恢复机制：

```
┌─────────────────────────────────────────────────────────────┐
│  任务级循环 (Task Level)                                      │
│  最多 max_quality_retries 次整体重试                          │
│  ┌───────────────────────────────────────────────────────┐  │
│  │  阶段级循环 (Stage Level)                               │  │
│  │  遍历 Plan 中的每个 PlanStep                            │  │
│  │  ┌─────────────────────────────────────────────────┐  │  │
│  │  │  推理级循环 (Reasoning Level)                    │  │  │
│  │  │  最多 max_iterations 次 LLM 推理迭代             │  │  │
│  │  │  Thought → Action → Observation → ...           │  │  │
│  │  └─────────────────────────────────────────────────┘  │  │
│  └───────────────────────────────────────────────────────┘  │
└─────────────────────────────────────────────────────────────┘
```

每一级循环都有自己的"失败检测器"和"恢复执行器"：

- **推理级**：检测 LLM 错误（网络超时、速率限制、上下文溢出等），恢复方式是重试或切换提供商
- **阶段级**：检测阶段结果质量（通过 QualityEvaluator），恢复方式是重试、重规划当前步骤或重规划后续步骤
- **任务级**：检测最终结果质量，恢复方式是重试原计划或重新生成整个计划

这三级循环形成了一个完整的故障隔离和恢复体系。低层级的失败尽量在低层级解决，只有低层级无法处理时才向上传播。

### 3.3 任务级恢复：两种策略

当整个任务的最终结果质量不达标时，Pipeline 有两种恢复策略：

**RETRY_SAME_PLAN**：保留原计划，重置上下文，重新执行。

这种策略适用于执行过程中出现偶发错误的情况。比如，某个工具调用因为网络问题失败了，导致该步骤的结果不完整，进而影响了最终结果的质量。在这种情况下，计划本身是合理的，只是执行过程中出了问题。重置上下文后重新执行，通常能得到正确的结果。

**REPLAN_ALL**：重新生成整个计划，从头执行。

这种策略适用于原计划本身就有问题的情况。比如，Planner 生成的计划遗漏了某个关键步骤，或者步骤的顺序不合理，导致最终结果无法满足用户需求。在这种情况下，重新执行原计划只会得到同样的错误结果，必须重新规划。

选择哪种策略由 `QualityEvaluator` 在评估时建议，而不是硬编码。这意味着 LLM 自己判断"这次失败是执行问题还是计划问题"，然后给出最合适的恢复建议。这比任何规则引擎都更准确，因为 LLM 能理解失败的语义。

### 3.4 阶段级恢复：代价递增的四档策略

这是整个恢复机制中设计最精细的部分。当某个阶段的执行结果不达标时，系统有四档恢复策略，代价从低到高：

```
RETRY_SAME_STEP    → 最低代价：丢弃当前阶段上下文，原地重试
REPLAN_THIS_STEP   → 低代价：重新生成当前步骤的计划，重试
REPLAN_FROM_HERE   → 中代价：重新生成当前及后续所有步骤，重试
REPLAN_ALL         → 最高代价：重置全部上下文，重新生成整个计划
```

**为什么要有这四档而不是直接 REPLAN_ALL？**

因为代价是真实存在的。每次重规划都需要调用 LLM，消耗 token，增加延迟。如果只是当前步骤的执行方式有问题，没必要推翻整个计划。代价递增的策略确保系统总是先尝试最便宜的恢复方式。

让我们用一个具体例子来说明：

假设任务是"分析销售数据并生成报告"，计划有 5 个步骤：
1. 连接数据库，查询销售数据
2. 清洗和预处理数据
3. 计算关键指标
4. 生成可视化图表
5. 撰写分析报告

如果第 3 步（计算关键指标）的结果不正确，应该怎么恢复？

- 如果是因为 SQL 查询写错了（比如 GROUP BY 字段选错了），`RETRY_SAME_STEP` 就够了——LLM 看到错误结果后会修正查询
- 如果是因为第 3 步的计划描述不够清晰，导致 LLM 不知道要计算哪些指标，`REPLAN_THIS_STEP` 更合适——重新生成第 3 步的计划，明确指定要计算的指标
- 如果是因为第 2 步的数据清洗有问题，导致第 3 步的输入数据就是错的，`REPLAN_FROM_HERE` 更合适——从第 2 步开始重新规划
- 如果是因为整个计划的分析思路就不对，`REPLAN_ALL` 才是正确选择

### 3.5 自动升级机制：防止死循环

有一个微妙但重要的设计：**恢复策略会自动升级**。

如果同一步骤连续 2 次 `RETRY_SAME_STEP` 都失败了，系统会自动将恢复策略升级到 `REPLAN_THIS_STEP`。这防止了一种常见的死循环：LLM 每次都建议"重试"，但问题根本不是执行问题，而是计划本身有缺陷。

```python
# 升级链：代价从低到高
escalation = {
    RETRY_SAME_STEP  → REPLAN_THIS_STEP,
    REPLAN_THIS_STEP → REPLAN_FROM_HERE,
    REPLAN_FROM_HERE → REPLAN_ALL,
}
# 触发条件：同一步骤连续 2 次相同失败
if same_failure_count >= 2:
    action = escalate(action)
```

这个机制背后的逻辑是：如果同样的恢复策略连续失败两次，说明这个策略不足以解决问题，需要升级到更激进的策略。这是一种自适应的恢复机制，不需要人工干预。

同时，系统还设置了全局上限：每步最多 `max_replan_stage_retries`（默认 3）次恢复，全局最多 `max_total_replan_count`（默认 8）次重规划。这防止了系统在一个无法解决的问题上无限循环。

### 3.6 推理级循环：ReAct 的实现

最内层的推理循环实现了 ReAct 范式。每次迭代的完整流程：

**第一步：轮询用户指令（非阻塞）**

在每次推理迭代开始时，系统会非阻塞地检查是否有用户指令（取消、引导等）。这个检查是非阻塞的，如果没有指令，立即继续执行，不会等待。

这个设计让用户可以在任务执行过程中随时干预：发送取消指令立即停止任务，发送引导指令（比如"注意，数据库中的日期格式是 YYYY-MM-DD"）会被注入到上下文中，影响后续的推理。

**第二步：构建上下文窗口**

调用 `ContextManager.get_context_window(provider_name)`，这个方法会：
- 对消息序列进行修复（五步修复管道）
- 根据 token 预算进行截断（如果需要）
- 返回可以直接发给 LLM 的 `ContextWindow` 对象

**第三步：调用 LLM 获取决策**

通过 `ReasoningManager.reason_once()` 调用 LLM，得到一个 `NextDecision` 对象，包含决策类型和相关数据。

**第四步：根据决策类型分支处理**

- `FINAL_ANSWER`：阶段完成，调用 `stage.complete(answer)`，退出循环
- `TOOL_CALL`：执行工具，把工具结果作为 observation 注入上下文，继续循环
- `CLARIFICATION_NEEDED`：向用户请求澄清，等待用户回复后继续
- `PAUSED`：等待用户发送 RESUME 指令后继续
- `CONTINUE`：LLM 有中间思考但还没有最终答案，注入 assistant 消息，继续循环

这个循环最多运行 `max_iterations`（默认 60）次，超出后触发模型切换，而不是直接失败。这是因为迭代次数超限通常意味着 LLM 陷入了某种循环，切换到不同的提供商可能会打破这个循环。

## 4. 任务分析：让 Agent 真正理解任务

### 4.1 为什么需要任务分析？

大多数 Agent 框架收到用户输入后，直接开始规划和执行。NanoAgent 在这之前多了一个关键步骤：**任务分析（Task Analysis）**。

这个步骤的价值在于：**把一个模糊的自然语言请求，转化为一个结构化的、机器可处理的任务描述**。

为什么这很重要？考虑这样一个用户请求："帮我分析一下上个季度的销售情况"。

这个请求包含很多模糊性：
- "上个季度"是哪个季度？需要根据当前日期计算
- "销售情况"包括哪些维度？总销售额、同比增长、分产品线、分地区？
- 数据在哪里？数据库？Excel 文件？
- 输出格式是什么？文字报告？图表？表格？

如果直接把这个模糊的请求交给 Planner，生成的计划很可能不够精准，执行过程中会遇到各种问题。任务分析的作用就是在执行之前，把这些模糊性尽可能消除。

### 4.2 分析产出的信息

`Analyzer` 通过 LLM 从用户输入中提取以下信息：

**任务语义层面**：

`task_type` 标识任务的类型，比如"数据分析"、"代码生成"、"信息检索"、"文档处理"等。这个字段直接影响模型路由——不同类型的任务适合不同的 LLM 提供商。

`intent` 捕捉用户的真实意图，有时和字面意思不同。比如，"帮我看看这段代码有没有问题"的真实意图可能是"代码审查并给出改进建议"，而不只是"找 bug"。

`task_goal` 描述任务的最终目标，用于在整个执行过程中保持方向一致。每个阶段的执行提示词都会包含 `task_goal`，确保 LLM 不会在细节中迷失方向。

`entities` 提取任务中涉及的关键实体，并进行规范化处理。比如：
- "上周五" → "2026-05-15"（具体日期）
- "AAPL" → "AAPL"（股票代码，已是标准格式）
- "销售数据库" → 需要进一步确认具体的数据库名称

实体规范化很重要，因为 LLM 在后续步骤中需要使用这些实体，规范化后的格式更不容易出错。

**执行约束层面**：

`action_constraints` 捕捉用户的行为约束，比如"不要修改原始文件"、"只查询不写入"、"不要调用外部 API"等。这些约束会注入到每个阶段的执行提示词中，确保 Agent 不会做出用户不希望的操作。

`output_constraints` 描述输出格式要求，比如"输出 Markdown 格式"、"结果要包含数据来源"、"不超过 500 字"等。这些约束在质量评估时作为评估标准之一。

`risks` 识别任务的潜在风险，比如"数据可能过时"、"成本可能超支"、"任务范围可能蔓延"等。这些风险信息会注入到计划生成提示词中，让 Planner 在生成计划时考虑这些风险。

**工具匹配层面**：

`tool_matches` 是任务分析中最有工程价值的输出之一。Analyzer 对每个可用工具计算相关性评分（0.5-1.0），低于 0.5 的工具直接排除，高于阈值（默认 0.65）的工具才会出现在 LLM 的工具列表中。

这个评分不是简单的关键词匹配，而是语义层面的相关性判断。比如，对于"分析 Excel 销售数据"这个任务，`excel` 工具的评分会很高，`flight_search` 工具的评分会很低（接近 0），`run_python` 工具的评分会中等（因为 Python 也可以处理 Excel，但不如专用工具）。

**路由提示层面**：

`routing_hints` 是给模型路由器的结构化提示，包括：
- `required_capability_tags`：任务需要的能力标签（如 "code"、"tool_use"、"long_context"）
- `estimated_context_tokens`：预估的上下文 token 数（用于过滤上下文窗口不够大的提供商）
- `latency_sensitive`：是否对延迟敏感（影响提供商选择）
- `cost_sensitive`：是否对成本敏感（影响提供商选择）

### 4.3 分析结果如何影响后续流程

任务分析的结果不只是给 Planner 看的，它贯穿整个执行流程：

**影响模型路由**：`routing_hints` 直接输入到 `CapabilityMatchStrategy` 的评分算法中，影响哪个 LLM 提供商被选为主选。

**影响工具过滤**：`tool_matches` 中的评分决定向 LLM 暴露哪些工具。这个过滤在计划生成后还会再做一次——Planner 在生成计划时也会对工具重新评分（`planner_score`），最终取两次评分的最大值与阈值比较。

**影响计划生成**：`entities`、`constraints`、`risks` 都会注入到 Planner 的提示词中，帮助生成更精准的计划。比如，如果 `risks` 中包含"数据可能过时"，Planner 可能会在计划中加入"验证数据时效性"的步骤。

**影响阶段执行**：`task_goal` 和 `intent` 注入每个阶段的提示词，保持执行方向一致。这防止了一种常见问题：LLM 在执行某个具体步骤时，忘记了整体任务的目标，做出了局部正确但全局错误的决策。

**影响质量评估**：`output_constraints` 作为评估标准之一。如果用户要求"输出 Markdown 格式"，但最终结果是纯文本，质量评估会标记为不通过。

### 4.4 知识与偏好的注入

任务分析阶段还会从两个外部来源加载信息：

**历史知识**：从向量数据库中检索与当前任务语义相似的历史知识条目。比如，如果之前执行过类似的数据分析任务，相关的数据库 Schema、常用查询模式、数据质量问题等会被检索出来，注入到当前任务的上下文中。

这个机制的价值在于：Agent 不需要每次都从零开始探索。如果之前已经发现了某个数据库的 Schema，下次执行类似任务时可以直接使用，不需要再次查询。

**用户偏好**：从偏好库中检索用户的历史偏好。比如，用户之前表达过"输出结果要包含可视化图表"，这个偏好会被检索出来，影响当前任务的执行方式。

这两个机制让 Agent 具备了"记忆"能力，随着使用次数增加，执行质量会逐渐提升。这是 NanoAgent 区别于一次性 Agent 的重要特性。

### 4.5 低置信度时的处理

任务分析的结果包含一个 `confidence` 字段（0-1），表示 Analyzer 对分析结果的置信度。当置信度低于阈值时，系统会触发澄清流程：

`implicit_needs` 字段包含 Analyzer 认为需要澄清的问题列表。这些问题会通过 `UserClarificationRequested` 事件发布，等待用户回复后再继续执行。

这个设计避免了一种常见问题：在任务描述模糊的情况下，Agent 基于错误的假设执行了很长时间，最后发现方向完全错了。提前澄清虽然增加了一点交互成本，但避免了更大的浪费。

## 5. 智能模型路由：不只是轮询

### 5.1 问题背景

当你有多个 LLM 提供商可用时，如何选择最合适的那个？

最简单的方案是轮询或随机选择，但这忽略了一个重要事实：**不同的 LLM 在不同类型的任务上有显著的能力差异**。Claude 在长文本理解和代码生成上表现出色，DeepSeek 在数学推理上有优势，Qwen 对中文任务更友好，MiniMax 在某些特定场景下成本更低。

如果你有一个需要复杂数学推理的任务，把它发给一个不擅长数学的提供商，结果质量会明显下降，甚至需要多次重试才能得到正确答案。这不只是质量问题，也是成本问题——错误的提供商选择会导致更多的重试，消耗更多的 token。

NanoAgent 的模型路由系统试图解决这个问题：**根据任务特征，自动选择最合适的提供商**。

### 5.2 CapabilityMatchStrategy：多信号加权评分

默认的路由策略 `CapabilityMatchStrategy` 对每个候选提供商计算一个综合评分，综合考虑多个维度的匹配程度：

**正向信号**（任务与提供商能力的匹配程度）：

| 信号 | 权重 | 设计意图 |
|------|------|---------|
| 任务类型精确匹配提供商偏好类型 | +8 | 最强信号，直接命中 |
| 所需能力标签命中提供商标签 | +5/个 | 能力维度匹配 |
| 认知复杂度层级覆盖 | +3 | 提供商能处理该难度 |
| 场景描述 Jaccard 相似度匹配 | +2/个 | 语义层面的场景匹配 |
| 需要工具调用且提供商支持 | +3 | 工具能力匹配 |
| API 稳定性加成 | +0~+5 | 可靠性权重 |

**负向惩罚**（风险和约束）：

| 惩罚条件 | 权重 | 设计意图 |
|----------|------|---------|
| 预估 token 数超过上下文窗口 70% | -5 | 防止上下文溢出 |
| 延迟敏感但提供商响应慢 | -3 | SLO 保障 |
| 成本敏感但提供商价格高 | -3 | 成本约束 |
| 用户偏好低成本/低延迟 | -2 | 软约束 |

评分最高的提供商成为主选，其余按分数排序形成备用链。

**为什么用 Jaccard 相似度而不是向量相似度？**

Jaccard 相似度计算的是两个词集合的交集比例，计算成本极低（不需要向量化），对于短文本（场景描述通常只有几个词）效果足够好。向量相似度虽然更准确，但需要额外的嵌入模型调用，增加了路由的延迟和成本。在路由这个场景下，Jaccard 是更合适的权衡。

**认知复杂度层级的设计**：

系统定义了 L1-L4 四个复杂度层级：
- L1：单步、模板化、低幻觉要求（寒暄、格式化、标签分类）
- L2：单步推理、常识、短上下文（客服问答、邮件起草、基础翻译）
- L3：多步推理、代码、分析（代码审查、数据分析、报告生成）
- L4：深度推理、创意、长链思维（架构设计、数学证明、策略规划）

每个提供商配置了它能处理的复杂度层级列表。一个能处理 L4 任务的提供商，当然也能处理 L1-L3 的任务（高层级覆盖低层级）。这个设计确保了路由的合理性：不会把 L4 的复杂任务发给只能处理 L1-L2 的轻量级模型。

### 5.3 策略可插拔

路由策略通过 `RoutingStrategy` 协议定义，可以在运行时替换：

```python
# 内置策略 1：语义能力匹配（默认）
model_selector.set_strategy(CapabilityMatchStrategy())

# 内置策略 2：纯成本/延迟优先
model_selector.set_strategy(CostLatencyStrategy(weight_cost=0.7, weight_latency=0.3))

# 自定义策略
model_selector.set_strategy(MyCustomStrategy())
```

这个设计的价值在于：路由逻辑和执行逻辑完全解耦。你可以在不修改任何执行代码的情况下，切换路由算法。

`CostLatencyStrategy` 是另一个内置策略，完全忽略任务语义，只按成本和延迟排序。这适用于对成本极度敏感的场景，或者所有提供商能力差不多的情况。

### 5.4 熔断器：运行时健康感知

静态路由解决了"任务开始时选谁"的问题，但无法处理"执行过程中提供商突然不可用"的情况。

每个提供商都有一个独立的熔断器（Circuit Breaker），实现三态状态机：

```
CLOSED（正常）
    │ 连续失败次数 ≥ failure_threshold
    ▼
OPEN（熔断，拒绝请求）
    │ 冷却时间到期
    ▼
HALF_OPEN（探测，允许少量请求）
    ├─ 探测成功 → 回到 CLOSED
    └─ 探测失败 → 回到 OPEN（重置冷却）
```

熔断器的核心价值是**快速失败**：当一个提供商已经连续失败多次时，不要再浪费时间等待它的响应，直接切换到备用提供商。这大幅减少了故障期间的等待时间。

**HALF_OPEN 状态的设计**：

当熔断器冷却时间到期后，不是直接回到 CLOSED 状态，而是进入 HALF_OPEN 状态，允许少量探测请求通过。这是因为：提供商可能只是暂时恢复，还不稳定。HALF_OPEN 状态让系统在恢复稳定性之前谨慎地验证提供商是否真的恢复了。

**优先恢复高优先级提供商**：

当当前提供商失败时，系统不是简单地切换到下一个，而是：

1. 先检查是否有**更高优先级的提供商已经从熔断中恢复**（优先回归最优选择）
2. 如果没有，才切换到下一个可用提供商

这个"优先恢复高优先级"的设计，确保系统在故障恢复后能尽快回到最优状态，而不是一直使用次优提供商。

举个例子：假设优先级列表是 [Claude, DeepSeek, Qwen]，Claude 因为过载被熔断，系统切换到 DeepSeek。一段时间后，Claude 的熔断冷却时间到期，进入 HALF_OPEN 状态。下次需要切换提供商时，系统会优先尝试 Claude（因为它优先级更高），而不是继续使用 DeepSeek。

### 5.5 检查点中的路由状态保存

熔断器状态会被保存到检查点中。这是一个容易被忽视但很重要的细节。

如果不保存熔断器状态，任务从检查点恢复后，路由器会认为所有提供商都是健康的，可能再次选择之前已经失败的提供商，导致重复失败。保存熔断器状态后，恢复的任务会继承中断前的提供商健康状态，避免这个问题。

## 6. ReAct 推理引擎：结构化思考的实现

### 6.1 为什么选择 ReAct？

ReAct（Reasoning + Acting）是目前最成熟的 Agent 推理范式之一。它的核心思想是：**把 LLM 的推理过程显式化**，让每一步行动都有明确的思考依据。

相比于直接让 LLM 输出最终答案，ReAct 的优势在于：

**可追溯**：每个工具调用都有对应的 Thought 解释为什么要调用。当结果不对时，你可以回溯推理链，找到是哪一步的思考出了问题。

**可纠错**：观察到工具结果后，LLM 可以更新推理，而不是盲目继续。如果工具返回了意外的结果，LLM 会在下一个 Thought 中分析这个结果，调整后续的行动计划。

**可调试**：推理链条完整保留在上下文中，便于排查问题。当 Agent 给出错误答案时，你可以看到完整的推理过程，理解它是如何得出这个答案的。

**抗幻觉**：ReAct 的规则明确要求"永远不要幻觉事实、输出或来源"，并且通过工具调用来验证信息，而不是依赖 LLM 的内部知识。这大幅减少了幻觉问题。

### 6.2 系统提示词的工程设计

ReAct 的效果很大程度上取决于系统提示词的质量。NanoAgent 的系统提示词包含几个关键设计：

**明确的行为规则**，而不是模糊的指导：

```
规则 1：分解复杂任务；从对话历史和观察结果推理，不要凭假设
规则 2：每次观察后，在下一步行动前更新你的计划
规则 3：信息不足或模糊时，明确说明。永远不要幻觉事实、输出或来源
规则 4：工具失败时，读取错误，调整参数或策略，重试。不要在第一次失败后放弃
规则 5：以简洁、有依据的最终答案结束
```

这些规则的设计有几个值得注意的地方：

规则 1 强调"从对话历史和观察结果推理"，而不是"从你的知识推理"。这是一个重要的区别——Agent 应该基于实际观察到的信息做决策，而不是依赖 LLM 的内部知识（内部知识可能过时或不准确）。

规则 4 明确要求工具失败时要重试，而不是放弃。这与系统的整体设计理念一致：失败是常态，重要的是如何从失败中恢复。

**工具选择的优先级规则**（first match wins）：

```
简单数学/单函数 → calculator
多步数据处理/numpy/pandas → run_python
纯文本/CSV 文件 → file
Excel 文件 → excel（先用 inspect 检查布局）
Shell 命令 → shell（避免长时间运行或交互式命令）
SQL 数据库 → SQL 工具（先检查 schema；始终用参数化查询）
语义/模糊查找 → 向量搜索工具
当前时间 → current_time
网络事实/近期事件 → search
```

这个优先级规则解决了一个常见问题：LLM 在面对多个可用工具时，往往会选择"万能"工具（如 run_python）而不是最合适的专用工具。明确的优先级规则引导 LLM 做出更精准的工具选择。

比如，对于"计算 sqrt(144)"这个简单任务，如果没有优先级规则，LLM 可能会选择 `run_python`（写一段 Python 代码来计算）。但实际上，`calculator` 工具更合适——它更轻量，不需要启动 Python 解释器，也不需要处理代码执行的安全问题。

**三个完整的 few-shot 示例**，覆盖典型场景：

示例 1（事实查询）展示了如何使用 search 工具查找信息，然后基于搜索结果进行推理，得出最终答案。关键点是：不要凭记忆回答，要通过工具验证。

示例 2（结构化数据查询）展示了"schema 优先"的工作模式：在查询数据库之前，先检查 schema，了解表结构，然后再写查询。这防止了一种常见错误：直接写查询，但字段名或表名写错了。

示例 3（多工具链式调用）展示了如何协调多个工具完成一个复杂任务：读取文件 → 用 Python 处理数据 → 写入结果文件。关键点是：每个工具调用都有明确的目的，工具之间的数据传递通过 `context_vars` 机制实现。

### 6.3 阶段提示词的动态注入

除了 ReAct 系统提示词，每个阶段开始时还会注入一个动态生成的阶段提示词，包含：

- 当前阶段的目标和描述
- 关键结果指标（用于判断阶段是否完成）
- 输入依赖（前序步骤的输出）
- 行为约束（不能做什么）
- 风险提示（需要注意什么）
- 是否是最后一步（影响输出格式要求）
- 上次恢复的反馈（如果是重试，告诉 LLM 上次哪里出了问题）

这个动态注入机制确保了每个阶段的 LLM 调用都有足够的上下文，不需要 LLM 从整个对话历史中自己推断当前应该做什么。

### 6.4 策略可插拔

`ReActStrategy` 实现了 `Strategy` 接口，这意味着推理范式本身是可替换的：

```python
class Strategy(ABC):
    def get_strategy_system_prompt(self) -> str: ...
    def build_llm_request(self, request) -> UnifiedLLMRequest: ...
    def parse_llm_response(self, response) -> NextDecision: ...
    def format_tool_observation(self, tool_call, result) -> LLMMessage: ...
```

如果你想实现 Chain-of-Thought、Tree-of-Thought 或其他推理范式，只需实现这个接口，不需要修改任何执行逻辑。

这个设计的价值在于：推理策略的演进不会影响系统的其他部分。当有更好的推理范式出现时，可以无缝替换，而不需要重写整个执行引擎。

## 7. 上下文管理：最难的工程问题

如果说三级循环是 NanoAgent 最核心的**架构设计**，那么上下文管理就是最核心的**工程挑战**。

在实际开发中，上下文管理踩的坑比任何其他模块都多。这一章会详细讲清楚我们是如何解决这些问题的。

### 7.1 问题的复杂性

LLM 的上下文窗口是有限的，但 Agent 执行复杂任务时产生的消息可能非常多：

- 每次 LLM 推理产生一条 assistant 消息
- 每次工具调用产生一条 tool 消息（包含工具参数）
- 每次工具返回产生一条 tool_result 消息（包含执行结果）
- 多步骤任务可能有几十甚至上百条消息

当消息总量超过上下文窗口时，必须截断。但截断不是简单地删掉最旧的消息，因为：

**约束 1：tool_use 和 tool_result 必须成对出现**

如果删掉了 tool_use 但保留了 tool_result，大多数 LLM API 会报错。反过来，如果删掉了 tool_result 但保留了 tool_use，LLM 会认为工具调用还没有完成，可能重复调用同一个工具。

**约束 2：第一条消息必须是 user 角色**

这是所有主流 LLM API（OpenAI、Anthropic、Qwen 等）的要求。如果截断后第一条消息变成了 assistant 或 tool，API 会报错。

**约束 3：不能有连续的同角色消息**

Anthropic API 明确拒绝连续的 user 或 assistant 消息。这在截断后很容易出现：如果删掉了某条 assistant 消息，可能导致两条 user 消息相邻。

**约束 4：阶段边界必须可追踪**

当某个阶段执行失败需要回滚时，需要精确删除该阶段产生的所有消息，而不影响其他阶段的消息。如果阶段边界信息丢失，就无法做到精确回滚。

**约束 5：检查点恢复后的一致性**

从检查点恢复时，需要把保存的对话历史重新加载到上下文中。加载后的消息序列必须满足上述所有约束，否则恢复后的第一次 LLM 调用就会失败。

这五个约束相互交织，使得上下文管理成为整个系统中最复杂的工程问题。

### 7.2 双缓冲设计：ctx_window 与 history 分离

`ContextManager` 维护两个独立的消息列表：

```
_ctx_window  ← 当前活跃上下文（可增删）
_history     ← 完整追加历史（只增不删）
```

**为什么要分离？**

`_ctx_window` 是发给 LLM 的实际内容，需要根据 token 预算动态调整。`_history` 是完整的审计记录，永远不删除。

这两个列表的用途完全不同：

`_ctx_window` 用于：
- 构建发给 LLM 的请求（`get_context_window()`）
- 阶段回滚（删除失败阶段的消息）
- 检查点保存（保存当前活跃上下文）

`_history` 用于：
- 知识提取（从完整对话历史中提取有价值的信息）
- 偏好学习（从完整对话历史中学习用户偏好）
- 审计和调试（完整记录任务执行过程）

当阶段执行失败需要回滚时，我们从 `_ctx_window` 中删除该阶段的消息，但 `_history` 保持完整。这意味着即使某个阶段被回滚了，它的执行记录仍然保留在历史中，可以用于后续的分析和学习。

**内存代价**：双缓冲设计的代价是内存占用翻倍。对于长任务，`_history` 可能积累大量消息。但这个代价是值得的——完整的历史记录对于知识提取和调试来说是不可替代的。

### 7.3 阶段边界追踪：基于消息 ID 而非索引

每条消息都携带一个 `stage_index` 字段，标记它属于哪个执行阶段。`ContextManager` 通过 `StageRecord` 追踪每个阶段的消息边界：

```
StageRecord {
    stage_index: 2,
    message_ids: ["msg-001", "msg-002", "msg-003", ...],
    completed: false,
    dropped: false
}
```

当需要删除某个阶段的消息时（比如 `RETRY_SAME_STEP`），直接按 `stage_index` 过滤，而不是依赖消息在列表中的位置。

**为什么用 stage_index 而不是消息位置？**

因为截断操作会改变消息的位置。如果用位置来标记阶段边界，截断后边界就失效了。用 `stage_index` 字段标记，无论消息怎么移动，边界信息始终准确。

举个例子：假设阶段 2 的消息在 `_ctx_window` 中的位置是 [10, 11, 12, 13]。如果截断操作删除了前 5 条消息，阶段 2 的消息位置变成了 [5, 6, 7, 8]。如果用位置来标记边界，这时候边界信息就错了。但如果用 `stage_index` 字段，每条消息的 `stage_index` 仍然是 2，过滤操作仍然正确。

**StageRecord 的生命周期**：

- `begin_stage(stage)`：创建 StageRecord，设置 `active_stage_index`
- 每次 `add_message()`：如果 `active_stage_index` 不为 None，把消息 ID 记录到对应的 StageRecord
- `end_stage(stage, success=True)`：标记 StageRecord 为 completed
- `drop_latest_stage_context()`：标记 StageRecord 为 dropped，从 `_ctx_window` 中删除该阶段的所有消息

### 7.4 上下文修复管道：五步自动修复

每次调用 `get_context_window()` 时，都会运行一个五步修复管道，确保发给 LLM 的消息序列是合法的：

```
原始消息列表
    │
    ▼ Step 1: _drop_leading_tool_results()
    │  删除出现在任何 tool_use 之前的孤立 tool_result 消息
    │  （这种情况在截断后可能出现：截断删掉了 tool_use，但保留了 tool_result）
    │
    ▼ Step 2: _ensure_first_message_is_user()
    │  删除开头的非 user 消息，直到第一条 user 消息
    │  （所有主流 LLM API 要求对话以 user 开始）
    │
    ▼ Step 3: _repair_tool_pairs()
    │  检查每个 tool_use 是否有对应的 tool_result
    │  对于没有 result 的 tool_use，注入合成的错误结果
    │  对于没有对应 tool_use 的 tool_result，直接删除
    │
    ▼ Step 4: _drop_trailing_tool_use()
    │  删除消息列表末尾的 tool_use 消息（没有对应 result）
    │  （Step 3 的安全网，防止边缘情况）
    │
    ▼ Step 5: _merge_consecutive_same_role()
       合并相邻的同角色消息（tool_use 和 tool_result 除外）
       （Anthropic API 拒绝连续的 user 或 assistant 消息）
```

这个修复管道是防御性编程的典型案例。每一步都在处理一种可能出现的非法状态，确保无论上游发生什么（截断、阶段回滚、检查点恢复），发给 LLM 的消息序列始终合法。

**Step 3 的细节**：`_repair_tool_pairs()` 是最复杂的一步。它需要处理多工具调用的情况（一个 assistant 消息可能包含多个 tool_use），以及工具调用结果乱序的情况（某些提供商的响应中，tool_result 的顺序可能与 tool_use 不一致）。

实现上，它维护一个 `pending` 字典，key 是 tool_call_id，value 是对应的 stage_index。遍历消息列表时：
- 遇到 tool_use：把所有 call_id 加入 pending
- 遇到 tool_result：从 pending 中移除对应的 call_id
- 遇到下一个 assistant 消息或列表结束：对 pending 中剩余的 call_id，注入合成的错误结果

**Step 5 的细节**：合并连续同角色消息时，需要特别处理 tool_use 和 tool_result 消息——这两种消息不能合并，因为它们携带结构化的元数据（call_id、tool_name 等），合并会破坏这些元数据。

### 7.5 Token 预算管理：角色分配制

上下文窗口的 token 预算不是平均分配的，而是按角色分配：

```
总预算 (total_budget)
    │
    ├─ 预留区 (reserved_tokens = total_budget × reserve_ratio)
    │       用于 LLM 响应输出 + 未来可能的摘要调用
    │       这部分不能被输入消息占用
    │
    └─ 可用区 (available_tokens = total_budget - reserved_tokens)
            按角色比例分配：
            ├─ system 消息：ratio_system × available
            ├─ user 消息：ratio_user × available
            ├─ assistant 消息：ratio_assistant × available
            └─ tool 消息：ratio_tool × available
```

**为什么要预留区？**

如果输入消息把 token 预算用满了，LLM 就没有空间输出响应了。预留区确保 LLM 始终有足够的 token 来生成完整的回复。

这个问题在实践中比想象的更常见。当任务执行到后期，上下文中积累了大量的工具调用结果（有些工具的输出可能很长），很容易把 token 预算用满。如果没有预留区，LLM 的响应会被截断，导致工具调用参数不完整，进而导致工具执行失败。

**为什么要按角色分配而不是总量控制？**

不同角色的消息有不同的重要性和压缩空间：

- system 消息包含关键指令（ReAct 系统提示、阶段提示），不应该被截断
- user 消息包含任务描述和用户指令，重要性高
- assistant 消息包含 LLM 的推理过程，可以适当压缩（保留最近的，删除较早的）
- tool 消息（工具执行结果）往往很长，但可以大幅压缩（只保留关键信息）

按角色分配让截断策略更精细：当 token 超限时，优先压缩 tool 消息，其次是较早的 assistant 消息，最后才考虑 user 消息。

### 7.6 上下文截断策略：保留最近，压缩历史

当消息总量超过预算时，`ContextTruncator` 执行截断。截断策略的核心原则是：

**保留最近的推理轨迹，压缩或删除较早的历史**。

这个原则背后的逻辑是：LLM 在推理时，最近的上下文比较早的上下文更重要。当前步骤的推理需要看到最近几次工具调用的结果，但不一定需要看到第一步的详细执行过程。

**具体截断流程**：

1. **计算当前 token 使用量**：对 `_ctx_window` 中的所有消息进行 token 估算（使用字符/token 比例快速估算，不调用 tokenizer）

2. **确定需要删除的 token 数**：`需要删除 = 当前使用量 - 可用预算`

3. **从头部开始删除**：按时间顺序，从最旧的消息开始删除，直到释放足够的 token 空间

4. **保护 tool_use/tool_result 配对**：不拆散工具调用对，整对删除或整对保留。如果删除一条 tool_use 消息，必须同时删除对应的所有 tool_result 消息

5. **摘要替代（可选）**：对于被删除的历史段落，可以选择调用 LLM 生成一段摘要，注入到上下文中，保留关键信息而不是完全丢弃

6. **截断后修复**：截断完成后，重新运行 `_repair_context()` 管道，确保结果合法

**摘要注入的权衡**：

摘要注入需要额外的 LLM 调用，增加延迟和成本。但对于长任务，早期阶段的关键信息（比如第一步发现的数据库 Schema、第二步清洗数据时发现的数据质量问题）如果完全丢失，可能导致后续步骤出错。

这是一个延迟/成本 vs 准确性的权衡，通过配置控制是否启用。对于对准确性要求高的任务，建议启用摘要注入；对于对延迟要求高的任务，可以禁用。

**Token 估算的精度问题**：

精确的 token 计数需要调用 tokenizer，这有一定的计算成本。NanoAgent 使用字符/token 比例（默认 3.5 字符/token）进行快速估算，在大多数情况下误差在 10% 以内。

对于不同的提供商，这个比例可能不同（中文文本的比例通常更低，因为一个汉字可能对应 2-3 个 token）。系统支持按提供商配置不同的估算比例，也支持接入真实的 tokenizer 进行精确计数。

### 7.7 上下文压力回调

`ContextManager` 支持注册压力回调：当 token 使用率超过阈值（默认 85%）时，自动触发回调通知上层模块。

```python
ctx.set_context_pressure_callback(
    callback=lambda pressure: logger.warning(f"Context pressure: {pressure:.1%}"),
    threshold=0.85
)
```

这让 Pipeline 可以提前感知上下文压力，在溢出之前主动采取措施（比如提前触发摘要，或者在下一个阶段开始时主动清理旧的上下文）。

### 7.8 流式消息支持

对于支持流式输出的 LLM，`ContextManager` 提供三阶段提交机制：

```python
stream_id = ctx.begin_streaming_message(role="assistant")
for chunk in llm_stream:
    ctx.append_streaming_chunk(stream_id, chunk)
msg_id = ctx.end_streaming_message(stream_id)  # 原子提交
```

流式消息在 `end_streaming_message()` 调用之前不会出现在上下文窗口中，确保 LLM 不会看到不完整的消息。

这个设计的关键是**原子提交**：消息要么完整地出现在上下文中，要么完全不出现，不存在"部分消息"的状态。这避免了一种潜在的问题：如果流式传输中途失败，不完整的消息不会污染上下文。

### 7.9 线程安全

`ContextManager` 的所有公共方法都通过 `threading.RLock` 保护。使用 RLock（可重入锁）而不是普通 Lock，是因为某些操作可能在持有锁的情况下调用其他需要锁的方法（比如 `get_context_window()` 内部调用 `_repair_context()`，而 `_repair_context()` 可能需要访问受锁保护的状态）。

在多线程环境中，以下场景可能同时发生：
- Agent 线程调用 `add_message()` 添加工具结果
- 用户线程通过 guidance 触发 `add_message()` 添加用户指令
- 异步检查点线程调用 `get_conversation_history()` 读取历史

RLock 确保这些操作不会相互干扰，同时避免了死锁。

## 8. LLM 网关：让 LLM 调用像调用本地函数一样可靠

### 8.1 设计目标

`LLMGateway` 的设计目标是：**调用方不需要关心 LLM 调用的任何可靠性问题**。

网络超时？自动重试。速率限制？自动退避。提供商过载？自动切换。JSON 格式错误？自动修复。调用方只需要传入请求，等待响应，不需要处理任何异常情况。

这个目标听起来简单，但实现起来需要处理大量的边缘情况。不同的 LLM 提供商有不同的错误格式、不同的速率限制策略、不同的重试建议。LLMGateway 把这些差异全部屏蔽掉，向上层提供一个统一的、可靠的接口。

### 8.2 统一的错误规范化

不同 LLM 提供商的错误格式各不相同：

- OpenAI 的速率限制错误：`{"error": {"type": "rate_limit_exceeded", "message": "..."}}`
- Anthropic 的过载错误：HTTP 529，body 包含 `"overloaded_error"`
- DeepSeek 的上下文过长错误：HTTP 400，body 包含 `"context_length_exceeded"`

`LLMGateway` 将所有这些错误规范化为 `LLMNormalizedError`，包含三层信息：

```
LLMNormalizedError
├─ code: LLMNormalizedErrorCode  ← 细粒度错误码（24 种）
├─ category: ErrorCategory       ← 粗粒度分类（8 种）
└─ caller_action: CallerAction   ← 机器可读的处理指令
        ├─ RETRY         → 立即重试，同提供商
        ├─ RETRY_BACKOFF → 退避后重试（尊重 Retry-After 头）
        ├─ SWITCH_MODEL  → 必须切换提供商
        ├─ DEGRADE       → 降级处理（减少上下文/工具/换模型）
        ├─ IGNORE        → 忽略（良性的空响应）
        └─ FATAL         → 终止，无法恢复
```

`caller_action` 是这个设计中最关键的部分。它把"发生了什么"和"应该怎么做"分离开来，让上层代码可以根据机器可读的指令做出决策，而不是解析错误消息字符串。

这种设计的优雅之处在于：当你添加一个新的 LLM 提供商时，只需要在提供商的 Client 实现中把该提供商的错误映射到 `LLMNormalizedError`，上层的所有重试和恢复逻辑不需要任何修改。

**错误码到处理动作的映射**：

| 错误码 | 处理动作 | 原因 |
|--------|---------|------|
| NETWORK_ERROR | RETRY | 网络问题通常是暂时的 |
| TIMEOUT | RETRY | 超时可以立即重试 |
| HTTP_5XX | RETRY_BACKOFF | 服务器错误需要等待 |
| PROVIDER_OVERLOADED | RETRY_BACKOFF | 过载需要等待 |
| RATE_LIMITED | RETRY_BACKOFF | 速率限制需要等待 |
| QUOTA_EXCEEDED | DEGRADE | 配额耗尽，降级处理 |
| CONTEXT_TOO_LONG | SWITCH_MODEL | 上下文过长，换有更大窗口的模型 |
| AUTH_FAILED | SWITCH_MODEL | 认证失败，换提供商 |
| CONTENT_FILTERED | DEGRADE | 内容被过滤，降级处理 |
| CONFIG_ERROR | FATAL | 配置错误，无法恢复 |

### 8.3 两层重试机制

**层 1：同模型重试**（针对 RETRY / RETRY_BACKOFF）

```python
for attempt in range(max_retries + 1):
    try:
        response = provider.generate(request)
        return response
    except LLMNormalizedError as exc:
        if exc.caller_action == FATAL:
            raise  # 立即终止
        if exc.caller_action in (RETRY, RETRY_BACKOFF):
            delay = exc.retry_after or backoff(attempt)  # 尊重 Retry-After
            sleep(delay)
            continue
        raise  # DEGRADE/SWITCH_MODEL 向上传播
```

退避策略使用**指数退避 + 全抖动（Full Jitter）**：`delay = random.uniform(0, backoff_cap)`。

全抖动比固定退避或指数退避更能避免"惊群效应"——当多个请求同时失败时，随机化的退避时间防止它们同时重试，避免再次触发速率限制。

**Retry-After 头的处理**：

不同提供商的 Retry-After 头格式不同：
- OpenAI：`{"error": {"retry_after": 30}}` （秒）
- Anthropic：`{"retry_after_ms": 30000}` （毫秒）
- 标准 HTTP：`Retry-After: 30` 头（秒）

`_extract_retry_after()` 函数按优先级依次尝试这三种格式，确保能正确解析各提供商的重试建议。

**层 2：模型降级**（针对 DEGRADE）

同一提供商可以配置多个备用模型（`model_fallback`）。当主模型触发 DEGRADE 时（比如上下文过长），自动尝试备用模型，而不是立即切换提供商。

这个设计的价值在于：同一提供商的不同模型通常有相同的 API 格式，切换成本很低。比如，当 `claude-3-5-sonnet` 的上下文窗口不够时，可以自动切换到 `claude-3-opus`（更大的上下文窗口），而不需要切换到完全不同的提供商。

### 8.4 JSON 修复：五步渐进式修复

LLM 有时会返回格式不标准的 JSON（比如带 Markdown 代码围栏、有尾随逗号、包含裸换行符）。`_repair_json()` 实现了五步渐进式修复：

```
Step 1: 直接 json.loads() → 成功则返回
Step 2: 剥离 ```json ... ``` 代码围栏 → 再次尝试
Step 3: 正则删除尾随逗号（,} 和 ,]）→ 再次尝试
Step 4: 转义字符串内的裸控制字符（\n, \r, \t）→ 再次尝试
Step 5: 从文本中提取第一个 {...} 或 [...] 子串 → 再次尝试
```

每一步都是对上一步的补充，而不是替代。这种渐进式修复策略在实践中能处理绝大多数 LLM 输出的 JSON 格式问题。

**为什么需要这么多步骤？**

因为 LLM 的输出格式问题是多样的，没有一种修复方法能处理所有情况：

- 代码围栏问题：LLM 经常把 JSON 包在 ` ```json ... ``` ` 中，即使你明确要求不要这样做
- 尾随逗号问题：LLM 有时会在 JSON 对象的最后一个字段后面加逗号，这在 JavaScript 中是合法的，但在标准 JSON 中不合法
- 控制字符问题：LLM 有时会在字符串值中包含裸换行符，这会导致 JSON 解析失败
- 前缀文本问题：LLM 有时会在 JSON 前面加一段解释性文字，比如"以下是结果："

五步修复策略按从简单到复杂的顺序尝试，找到第一个成功的方法就返回，不会做不必要的修复。

### 8.5 UnifiedLLMRequest：统一的请求格式

所有 LLM 调用都通过 `UnifiedLLMRequest` 发起，这个数据类统一了所有提供商的请求参数：

```python
@dataclass(slots=True)
class UnifiedLLMRequest:
    messages: list[LLMMessage]
    system_prompt: str | None = None
    tool_schemas: list[dict] | None = None
    max_tokens: int | None = None
    temperature: float | None = None
    model_override: str | None = None  # 覆盖默认模型（用于降级）
    json_mode: bool = False             # 强制 JSON 输出
    json_required_keys: list[str] | None = None  # JSON 必须包含的键
    enable_cache: bool = False          # 启用提示词缓存
    enable_thinking: bool = False       # 启用思维链（Claude 扩展思考）
```

`enable_thinking` 是一个特别有趣的字段。Claude 支持"扩展思考"（Extended Thinking）模式，在这个模式下，模型会先进行内部推理，然后再给出最终答案。对于复杂的推理任务，这个模式可以显著提高准确性。通过 `enable_thinking` 字段，可以在不修改任何其他代码的情况下，为特定的请求启用这个功能。

## 9. 检查点机制：长任务的生命线

### 9.1 问题场景：第 25 分钟的崩溃

想象这样一个场景：你让 Agent 帮你分析一份复杂的销售数据报告。任务包含 6 个步骤：连接数据库、清洗数据、计算各维度指标、生成可视化图表、撰写分析报告、导出最终文件。整个任务预计需要 30 分钟，调用 LLM 约 40 次，工具调用约 60 次。

任务跑到第 25 分钟，正在执行第 5 步"撰写分析报告"。这一步已经完成了 80%，LLM 正在生成最后一段结论。突然，网络抖动，LLM API 返回了一个 503 错误，重试三次后仍然失败。

如果没有检查点机制，你面对的是：

**时间损失**：25 分钟的执行时间归零，需要从头重来。

**金钱损失**：这才是更让人心痛的部分。40 次 LLM 调用，按 GPT-4 的价格估算，大约花费了 2-3 美元。这些钱就这么打水漂了。如果你用的是 Claude Opus，损失可能更大。更糟糕的是，重跑一次还要再花同样的钱。

**用户体验损失**：用户等了 25 分钟，看到的是一个错误信息。他们不知道任务执行到哪里了，不知道哪些步骤已经完成，不知道是否需要重新提交任务。这种不确定性比单纯的等待更让人沮丧。

**为什么 Agent 任务特别脆弱？**

普通软件任务失败了，通常可以快速重试，因为每次执行的代价很低（毫秒级，几乎零成本）。但 Agent 任务有三个特点让它特别脆弱：

第一，**执行时间长**。一个复杂的 Agent 任务可能需要几分钟到几十分钟，期间任何一个环节出问题都会导致整体失败。执行时间越长，遇到问题的概率越高。

第二，**调用成本高**。每次 LLM 调用都有真实的 API 费用。一个 30 分钟的任务可能花费几美元，从头重来意味着双倍成本。

第三，**状态不可重现**。Agent 任务的中间状态往往是不可重现的——第 3 步生成的数据分析结果，第 4 步的图表，这些都是 LLM 在特定上下文下生成的，重跑不一定得到完全相同的结果。

检查点机制就是为了解决这个问题：**让长任务在任何时间点崩溃后，都能从最近的成功节点继续，而不是从头开始**。


### 9.2 保存时机的设计：为什么是"评估通过后"

检查点的保存时机是一个关键设计决策。有几种选择：

**方案 A：每次工具调用后保存**

最细粒度的方案。每次工具执行完毕，立即保存检查点。

问题：工具调用非常频繁，一个阶段可能有 10-20 次工具调用。每次都保存意味着大量的磁盘 I/O，而且大多数中间状态并没有保存价值——一个阶段执行到一半的状态，恢复后也无法直接继续，还是需要重新执行这个阶段。

**方案 B：每次 LLM 推理后保存**

比方案 A 稍粗一些，但问题类似。LLM 推理的中间状态（比如"正在思考下一步用什么工具"）没有独立的恢复价值。

**方案 C：每个阶段完成后保存（不管质量如何）**

每当一个阶段的 ReAct 循环结束，LLM 给出了最终答案，就保存检查点。

问题：这个阶段的结果可能是错误的。如果我们保存了一个质量不合格的阶段结果，恢复后继续执行，后续阶段会基于这个错误结果继续，最终产出的任务结果也会是错误的。

**方案 D（NanoAgent 的选择）：每个阶段通过质量评估后保存**

只有当阶段结果通过了 `QualityEvaluator` 的评估，才保存检查点。

这个设计的核心洞察是：**检查点保存的是"已验证的进度"，而不是"已完成的工作"**。

"已完成"和"已验证"是两回事。一个阶段可能已经完成了（LLM 给出了答案），但答案是错误的（评估不通过）。如果保存了这个未验证的状态，恢复后继续执行，就是在错误的基础上继续构建，最终结果必然有问题。

只保存通过评估的阶段，确保了每个检查点都是一个"已知良好"的状态。从这个状态恢复，后续执行可以安全地依赖之前阶段的结果。

**保存时机的代码体现**：

```python
# 在 pipeline._execute_stages() 中
for step in plan.step_list[start_step_index:]:
    result = self._stage_executor.execute(step, task)
    
    # 只有阶段成功完成（包括通过评估），才保存检查点
    if result.success:
        CheckpointManager.save_async(
            CheckpointData(
                completed_step_index=step.order - 1,
                # ... 其他状态
            ),
            task_name=task.task_goal[:30],
        )
```

注意 `save_async`——检查点保存是异步的，在后台线程执行，不阻塞主执行流程。这是一个重要的性能优化：检查点保存涉及序列化和磁盘 I/O，如果同步执行，会增加每个阶段的延迟。


### 9.3 保存内容的完整性：每一个字段都有理由

`CheckpointData` 包含以下字段，每一个都有其存在的理由：

```python
@dataclass
class CheckpointData:
    task_id: TaskId
    user_id: UserId
    task_description: str          # 原始任务描述
    task: Task                     # 完整的 Task 对象（含分析结果）
    plan: Plan                     # 完整的执行计划
    completed_step_index: int      # 已完成的最后一步索引（0-based）
    conversation_history: list[LLMMessage]  # 完整对话历史
    tool_schemas: list[dict]       # 过滤后的工具 Schema
    model_selector_state: ModelSelectorState  # 模型路由状态（含熔断器）
    task_output_constraints: str   # 输出约束
    task_goal: str                 # 任务目标
    task_intent: str               # 任务意图
    task_recovery_feedback: str    # 上次任务级恢复的反馈
```

**为什么要保存 `conversation_history`？**

这是最显而易见的——对话历史是 LLM 推理的上下文。没有它，恢复后的 LLM 不知道之前做了什么，会重新开始。

但有一个细节值得注意：保存的是 `conversation_history`（完整历史），而不是 `ctx_window`（当前活跃上下文）。这是因为恢复时需要重建完整的上下文状态，包括已经被截断的历史消息。

**为什么要保存 `tool_schemas`？**

直觉上，工具 Schema 是静态的，可以在恢复时重新生成。但实际上，NanoAgent 在执行前会根据任务特征过滤工具（只保留相关工具），这个过滤结果是动态的。

如果恢复时重新过滤，可能得到不同的工具集（比如任务分析的随机性导致不同的过滤结果）。这会导致恢复后的执行与原始执行使用不同的工具，破坏了执行的一致性。

保存过滤后的工具 Schema，确保恢复后使用完全相同的工具集。

**为什么要保存 `model_selector_state`（含熔断器状态）？**

这是最容易被忽视的字段，但也是最重要的之一。

`ModelSelectorState` 包含了熔断器的状态：哪些提供商当前处于熔断状态，熔断计数是多少。

如果不保存这个状态，恢复后熔断器会重置为初始状态。这意味着：如果某个提供商在执行前 5 步时频繁失败，已经被熔断了，恢复后熔断器重置，系统会再次尝试这个不稳定的提供商，可能再次触发失败。

保存熔断器状态，让恢复后的系统"记住"之前遇到的提供商问题，继续使用已经验证可靠的提供商。

**为什么要保存 `task_recovery_feedback`？**

这个字段记录了上一次任务级评估失败时的反馈信息。

场景：任务执行完所有步骤，但任务级评估不通过，评估器给出了反馈"结果缺少对异常数据的处理"。系统决定重新规划并重新执行。在重新执行过程中，如果某个阶段通过了评估，保存检查点时需要把这个反馈也保存进去。

为什么？因为如果这次重新执行又在某个阶段崩溃了，从检查点恢复时，需要知道"这次执行是在修复什么问题"。没有这个反馈，恢复后的执行可能忘记了需要处理异常数据，再次产出不合格的结果。


### 9.4 恢复流程：优雅的代码复用

NanoAgent 的检查点恢复设计有一个特别优雅的地方：**恢复流程和正常执行流程共享同一个 `_execute_stages()` 方法**。

```python
def _run_from_checkpoint(self, checkpoint_path: str) -> TaskResult:
    data = CheckpointManager.load(checkpoint_path)
    
    # 恢复所有状态
    self._context_manager.reset()
    self._context_manager.replace_conversation_history(data.conversation_history)
    self._context_manager.set_tool_schemas(data.tool_schemas)
    self._context_manager.set_task(data.task)
    self._context_manager.set_plan(data.plan)
    self._model_selector.restore_state(data.model_selector_state)
    self._stage_executor.set_task_description(data.task_description)
    # ... 其他状态恢复
    
    # 复用同一个执行方法，只是从不同的起点开始
    return self._execute_stages(
        data.task, 
        data.plan, 
        data.task_description,
        start_step_index=data.completed_step_index + 1  # 从下一步开始
    )
```

`_execute_stages()` 接受一个 `start_step_index` 参数，指定从哪一步开始执行。正常执行时，这个参数是 0（从第一步开始）；从检查点恢复时，这个参数是 `completed_step_index + 1`（从下一步开始）。

**为什么这个设计是优雅的？**

对比另一种常见的设计：为恢复流程写一套独立的代码路径。

```python
# 不好的设计：两套代码路径
def _run_new_task(...):
    # 正常执行逻辑
    for step in plan.step_list:
        self._execute_step(step)

def _resume_from_checkpoint(...):
    # 恢复执行逻辑（几乎是 _run_new_task 的复制）
    for step in plan.step_list[start_index:]:
        self._execute_step(step)
```

两套代码路径意味着：每次修改执行逻辑，都需要同步修改两处。这是维护噩梦的来源。

共享代码路径的设计确保了：**恢复执行和正常执行的行为完全一致**。任何对执行逻辑的改进，自动适用于恢复流程。

**`start_step_index` 的语义**

`start_step_index` 是 0-based 的步骤索引。`completed_step_index` 记录的是最后一个成功完成的步骤的索引（也是 0-based）。

所以恢复时从 `completed_step_index + 1` 开始，跳过所有已完成的步骤，直接从下一个未完成的步骤继续。

举例：一个 6 步任务，前 3 步已完成（`completed_step_index = 2`），恢复时从第 4 步（`start_step_index = 3`）开始。


### 9.5 检查点的局限性与未来改进

当前的检查点实现有几个已知的局限性，值得坦诚地讨论。

**局限 1：pickle 序列化的风险**

NanoAgent 使用 Python 的 `pickle` 模块序列化 `CheckpointData`。pickle 是 Python 原生的序列化格式，支持几乎所有 Python 对象，使用简单。

但 pickle 有两个问题：

第一，**安全风险**。pickle 文件可以包含任意 Python 代码，加载不受信任的 pickle 文件可能导致代码执行漏洞。在 NanoAgent 的使用场景中，检查点文件由系统自己生成，不存在外部输入的问题，所以这个风险是可控的。但如果未来需要在网络上传输检查点文件，就需要换成更安全的序列化格式（比如 JSON 或 MessagePack）。

第二，**版本兼容性**。如果 `CheckpointData` 的结构在两次执行之间发生了变化（比如添加了新字段），旧的检查点文件可能无法正确加载。

**局限 2：Schema 变更导致的不兼容**

如果在保存检查点后、恢复执行前，`Plan` 或 `Task` 的数据结构发生了变化（比如添加了新字段、修改了字段类型），恢复时可能会遇到 `AttributeError` 或数据不一致的问题。

这在开发阶段尤其常见：你保存了一个检查点，然后修改了代码，再尝试恢复，发现检查点文件和新代码不兼容。

**局限 3：只有阶段级检查点，没有步骤内检查点**

当前的检查点粒度是"阶段"（一个 Plan Step）。如果一个阶段需要 20 分钟，在第 18 分钟崩溃，仍然需要重新执行整个阶段。

对于特别长的单个阶段，理想情况下应该有更细粒度的检查点（比如每 N 次工具调用保存一次）。但这会大幅增加实现复杂度，目前还没有实现。

**未来改进方向**：

1. **换用 JSON 序列化**：把 `CheckpointData` 中的所有字段都设计为 JSON 可序列化的，用 JSON 替代 pickle。这解决了安全风险和版本兼容性问题（JSON 格式更容易做向前兼容）。

2. **增量检查点**：不是每次保存完整状态，而是只保存增量变化。这可以大幅减少检查点文件的大小，特别是对话历史很长的情况下。

3. **检查点版本号**：在 `CheckpointData` 中加入版本号字段，加载时检查版本兼容性，提供清晰的错误信息。

## 10. 工具系统：安全与灵活的平衡

### 10.1 工具过滤：两遍打分的设计

NanoAgent 在执行任务前，会对所有可用工具进行过滤，只把相关工具的 Schema 放入 LLM 的上下文。这个过滤过程使用了两遍打分机制。

**为什么需要过滤工具？**

工具 Schema 会占用 token。如果系统有 20 个工具，把所有工具的 Schema 都放入上下文，可能消耗 2000-3000 个 token。对于简单任务，大多数工具是不相关的，这些 token 是浪费。

更重要的是，无关工具会干扰 LLM 的决策。当 LLM 面对 20 个工具时，它需要从中选择合适的工具，无关工具增加了选择的复杂度，可能导致 LLM 选错工具。

**第一遍：Analyzer 打分（`match_score`）**

任务分析阶段，`TaskAnalyzer` 会对每个工具进行相关性评分。这个评分基于任务描述和工具描述的语义相似度：这个工具对完成这个任务有多大帮助？

Analyzer 的视角是**任务整体**：它看的是整个任务描述，评估工具对整个任务的相关性。

**第二遍：Planner 打分（`planner_score`）**

计划生成阶段，`Planner` 在生成执行计划时，会对每个工具再次打分。这个评分基于计划的具体步骤：这个工具在执行计划的某个具体步骤时会被用到吗？

Planner 的视角是**执行细节**：它看的是具体的执行步骤，评估工具在实际执行中的使用可能性。

**两遍打分捕获不同的信息**

举一个具体例子：假设任务是"分析销售数据并生成报告"，系统有 `query_mysql_data`、`run_python`、`shell`、`travel_guide` 四个工具。

- `travel_guide`：Analyzer 打分 0.1（与销售分析无关），Planner 打分 0.1。两遍都低，过滤掉。
- `query_mysql_data`：Analyzer 打分 0.9（销售数据在数据库里），Planner 打分 0.9（计划第一步就是查询数据库）。两遍都高，保留。
- `run_python`：Analyzer 打分 0.7（数据分析可能需要 Python），Planner 打分 0.8（计划第二步是数据处理，用 Python）。保留。
- `shell`：Analyzer 打分 0.4（可能用到，但不确定），Planner 打分 0.2（计划里没有需要 shell 的步骤）。

对于 `shell` 这个工具，Analyzer 给了中等分（任务层面看起来可能有用），但 Planner 给了低分（具体计划里用不到）。最终取两者的最大值 0.4，低于阈值 0.65，过滤掉。

这就是两遍打分的价值：Analyzer 可能对某些工具过于乐观（"这个任务可能会用到"），Planner 的具体计划视角可以纠正这种过度乐观。反过来，Planner 可能对某些工具过于保守（计划里没有明确提到），Analyzer 的整体视角可以补充。

**过滤阈值**：默认 0.65，可通过配置调整。取两个分数的最大值，只要有一个分数超过阈值，工具就会被保留。


### 10.2 工具执行的安全设计：错误即数据

NanoAgent 工具系统的核心设计哲学是：**工具执行的错误是数据，不是异常**。

在传统的软件设计中，错误通常通过异常（Exception）传播：工具执行失败，抛出异常，调用方捕获异常，决定如何处理。

NanoAgent 的工具系统不这样做。所有工具的 `run()` 方法都返回 `ToolResult`，无论成功还是失败：

```python
@dataclass(slots=True)
class ToolResult:
    output: str           # JSON 格式的输出（成功时包含数据，失败时包含错误信息）
    success: bool         # 是否成功
    error: PipelineError | None = None  # 结构化错误信息
```

即使工具执行失败，也会返回一个 `ToolResult`，其中 `success=False`，`error` 包含结构化的错误信息。

**为什么这样设计？**

因为工具执行的结果（包括错误）需要被放回 LLM 的上下文中，让 LLM 看到并做出决策。

如果工具执行失败抛出异常，异常会被框架捕获，然后需要决定：是把错误信息注入上下文，还是直接终止执行？这个决策逻辑需要在框架层面实现，而不是让 LLM 参与。

如果工具执行失败返回 `ToolResult(success=False, error=...)`，这个结果会被正常地放入上下文，LLM 会看到工具失败的信息，然后自主决定：是换一个工具？是修改参数重试？还是告诉用户这个步骤无法完成？

**LLM 自我纠错的能力**

这个设计让 LLM 能够自我纠错。举个例子：

LLM 调用 `query_mysql_data` 工具，SQL 语句有语法错误，工具返回：
```json
{
  "success": false,
  "error": {
    "code": "SQL_QUERY_TOOL_ERROR",
    "message": "You have an error in your SQL syntax near 'FORM' at line 1"
  }
}
```

LLM 看到这个错误，意识到 `FORM` 应该是 `FROM`，修正 SQL 语句，重新调用工具。这个自我纠错过程完全在 LLM 的推理循环内完成，不需要框架层面的特殊处理。

如果工具执行失败抛出异常，这个自我纠错的机会就丢失了——框架捕获异常后，LLM 没有机会看到错误信息并做出调整。

**`ToolHandlerNode` 的异常捕获**

当然，工具的实现代码可能会抛出异常（比如数据库连接失败、文件不存在等）。`ToolHandlerNode` 负责捕获这些异常，并将其转换为 `ToolResult`：

```python
class ToolHandlerNode(BaseToolHandler):
    def process(self, tool_call: ToolCall) -> ToolResult:
        try:
            result = self._tool.run(tool_call.arguments)
            return result
        except TimeoutError as exc:
            return ToolResult(success=False, error=build_pipeline_error(TOOL_TIMEOUT, ...))
        except PipelineError as exc:
            return ToolResult(success=False, error=exc)
        except Exception as exc:
            return ToolResult(success=False, error=build_pipeline_error(TOOL_EXECUTION_ERROR, ...))
```

这个设计确保了：无论工具内部发生什么，调用方总是得到一个 `ToolResult`，而不是一个未处理的异常。


### 10.3 高危工具的安全边界

NanoAgent 内置了三个高危工具：`ShellTool`、`RunPythonTool`、`SQLQueryTool`。每个工具都有针对其特定攻击向量的安全设计。

**ShellTool：沙箱隔离**

Shell 工具的主要风险是命令注入和文件系统破坏。

防御措施：
- **工作目录隔离**：所有命令在任务专属的工作目录（`var/runtime/{task_id}/`）中执行，而不是项目根目录或系统目录。即使 LLM 生成了 `rm -rf /` 这样的命令，影响范围也被限制在任务工作目录内。
- **超时限制**：默认 15 秒超时，防止长时间运行的命令阻塞执行流程。
- **非零退出码处理**：命令执行失败（非零退出码）会被转换为结构化错误，而不是静默忽略。

值得注意的是，ShellTool **没有**对命令内容进行白名单过滤。这是一个有意的设计决策：命令过滤很难做到完整，而且会限制工具的灵活性。工作目录隔离提供了足够的安全边界，同时保留了工具的完整功能。

**RunPythonTool：多层沙箱**

Python 工具的风险更复杂：代码执行可以做几乎任何事情，包括访问文件系统、发起网络请求、消耗大量内存等。

防御措施分三层：

第一层，**静态导入检查**：在执行代码之前，用 AST 解析代码，检查所有 `import` 语句。如果发现被禁止的模块（`os`、`subprocess`、`socket` 等），直接拒绝执行，返回错误。

```python
_BLOCKED_IMPORTS = frozenset({
    "os", "sys", "subprocess", "shutil", "socket", "signal",
    "ctypes", "cffi", "multiprocessing", "threading",
    # ...
})
```

第二层，**受限内置函数**：执行代码时，用一个受限的 `__builtins__` 替换标准内置函数，移除了 `open`、`exec`、`eval`、`compile`、`__import__` 等危险函数。同时，`__import__` 被替换为一个守卫版本，在运行时再次检查导入的模块是否在白名单内。

第三层，**子进程隔离 + 资源限制**：代码在独立的子进程中执行（使用 `multiprocessing.Process`），并通过 `resource` 模块设置内存上限（256MB）和 CPU 时间上限（10秒）。即使代码绕过了前两层防御，资源限制也能防止它消耗过多系统资源。

**SQLQueryTool：只读强制**

SQL 工具的风险是 SQL 注入和数据修改。

防御措施：
- **参数化查询**：工具 Schema 明确要求使用参数化查询（`params` 字段），而不是字符串拼接。工具描述中也明确说明"Use placeholders instead of interpolating values directly"。
- **只读限制**：工具描述明确说明只支持 SELECT 语句，后端实现可以在数据库层面强制只读（比如使用只读数据库用户）。
- **行数限制**：默认最多返回 50 行，最大 1000 行，防止全表扫描导致的性能问题。


### 10.4 连续工具调用限制：防止死循环

在 ReAct 推理循环中，有一种特殊的失败模式：**工具调用死循环**。

**死循环的典型样子**

想象 LLM 在执行"查询用户数据"这个步骤：

```
第 1 次迭代：
  LLM 思考：我需要查询用户表
  LLM 调用：query_mysql_data(statement="SELECT * FROM users")
  工具返回：错误，表 'users' 不存在

第 2 次迭代：
  LLM 思考：查询失败了，我再试一次
  LLM 调用：query_mysql_data(statement="SELECT * FROM users")
  工具返回：错误，表 'users' 不存在

第 3 次迭代：
  LLM 思考：可能是大小写问题
  LLM 调用：query_mysql_data(statement="SELECT * FROM Users")
  工具返回：错误，表 'Users' 不存在

第 4 次迭代：
  LLM 思考：我再试一次原来的查询
  LLM 调用：query_mysql_data(statement="SELECT * FROM users")
  工具返回：错误，表 'users' 不存在
  ...
```

LLM 陷入了一个循环：它知道查询失败了，但不知道如何解决，于是反复尝试相同或相似的查询。这个循环可以持续很多次，消耗大量的 token 和时间，却没有任何进展。

**NanoAgent 的解决方案**

`StageExecutor` 维护一个连续工具调用计数器。每次 LLM 调用工具，计数器加 1；每次 LLM 给出非工具调用的响应（比如最终答案），计数器重置为 0。

当计数器超过阈值（默认 10 次），系统不会直接终止执行，而是**向上下文注入一条干预消息**：

```
[系统提示] 你已经连续调用工具 10 次。请停下来思考：
1. 当前的工具调用策略是否有效？
2. 是否需要换一种方法？
3. 如果问题无法通过工具解决，请直接给出你目前能提供的最佳答案。
```

**为什么注入消息而不是直接终止？**

直接终止会导致阶段失败，触发重试或重新规划，代价很高。

注入消息给了 LLM 一个"自我反思"的机会。很多时候，LLM 在看到这条提示后，会意识到自己陷入了循环，然后换一种策略（比如先查询数据库 Schema，再构造正确的查询）。

这种"软干预"比"硬终止"更优雅，也更符合 Agent 的自主性原则：我们不是强制终止 LLM 的行为，而是给它一个信号，让它自己做出调整。

### 10.5 工具扩展机制

添加一个新工具非常简单，只需要继承 `BaseTool` 并实现三个字段和一个方法：

```python
from tools.tool_base import BaseTool, build_tool_output
from schemas import ToolResult

class WeatherTool(BaseTool):
    name = "get_weather"
    description = "Get current weather for a city."
    parameters = {
        "type": "object",
        "properties": {
            "city": {"type": "string", "description": "City name"},
        },
        "required": ["city"],
        "additionalProperties": False,
    }

    def run(self, arguments: dict) -> ToolResult:
        city = arguments.get("city", "")
        # ... 实际实现
        return ToolResult(
            output=build_tool_output(success=True, data={"temperature": 25, "condition": "sunny"}),
            success=True,
        )
```

**自动发现机制**

`ToolRegistry` 支持自动发现工具，不需要手动注册：

```python
registry = ToolRegistry()
registry.auto_register(package_name="tools.impl")
```

`auto_register()` 会扫描指定包下的所有模块，找到所有继承了 `BaseTool` 的非抽象类，自动实例化并注册。

这个机制基于 Python 的 `pkgutil.walk_packages()` 和 `inspect.getmembers()`，可以递归扫描包的所有子模块。

**工具的 `reset()` 方法**

`BaseTool` 提供了一个 `reset()` 方法，在每个任务开始前调用，用于清理工具的任务级状态。

对于无状态工具（比如 `ShellTool`、`SQLQueryTool`），`reset()` 是空操作。对于有状态工具（比如 `RunPythonTool`，它维护了一个会话上下文），`reset()` 需要清理状态：

```python
class RunPythonTool(BaseTool):
    def __init__(self):
        self._session_context: dict = {}
    
    def reset(self):
        self._session_context.clear()  # 清理上一个任务的变量
```

### 10.6 run_python 工具的会话持久化设计

`RunPythonTool` 有一个特别有用的功能：**跨调用的变量持久化**。

**为什么需要变量持久化？**

考虑这样一个场景：LLM 需要用 Python 处理一个大型数据集。

如果没有变量持久化，每次调用 `run_python` 都是独立的，LLM 需要在每次调用中重新加载数据：

```python
# 第 1 次调用：加载数据并计算
import pandas as pd
df = pd.read_csv("sales_data.csv")  # 每次都要重新加载
result = df.groupby("region").sum()
print(result)

# 第 2 次调用：还需要 df，但它不存在了
import pandas as pd
df = pd.read_csv("sales_data.csv")  # 又要重新加载
filtered = df[df["amount"] > 1000]
print(filtered)
```

有了变量持久化，LLM 可以把 `df` 保存到会话中，后续调用直接使用：

```python
# 第 1 次调用：加载数据，保存到会话
import pandas as pd
df = pd.read_csv("sales_data.csv")
print(df.shape)
# context_vars: ["df"]  ← 告诉工具把 df 保存到会话

# 第 2 次调用：直接使用会话中的 df
result = df.groupby("region").sum()  # df 已经在会话中了
print(result)
```

**`context_vars` 机制**

工具调用时，LLM 可以通过 `context_vars` 参数指定哪些变量需要保存到会话：

```json
{
  "code": "df = pd.read_csv('data.csv')\nprint(df.shape)",
  "context_vars": ["df"]
}
```

执行完成后，工具会从命名空间中提取 `df` 的值，序列化后保存到 `_session_context`。下次调用时，`_session_context` 中的所有变量会被预加载到执行命名空间。

**序列化的限制**

只有 JSON 可序列化的值才能保存到会话。函数、类、lambda 等不可序列化的对象会被跳过。对于不可序列化的对象（比如 pandas DataFrame），工具会尝试用 `repr()` 保存其字符串表示，但这通常没有实际用途。

这个限制在实践中影响不大，因为 LLM 通常只需要保存数据（DataFrame、列表、字典等），而不是函数。

**`context` 参数：单次注入**

除了持久化的会话变量，工具还支持通过 `context` 参数注入单次使用的变量：

```json
{
  "code": "result = process(input_data)",
  "context": {"input_data": [1, 2, 3, 4, 5]},
  "context_vars": ["result"]
}
```

`context` 中的变量只在这次调用中有效，不会被保存到会话。这对于需要传入外部数据（比如从上一个工具调用获取的结果）的场景很有用。

## 11. 质量评估：让 Agent 自我审视

### 11.1 三个层次的评估：为什么不能少

NanoAgent 的质量评估分三个层次：计划评估、阶段结果评估、任务结果评估。这三个层次不是冗余的，每个层次解决不同的问题。

**如果只有任务级评估会怎样？**

任务执行完所有步骤后，评估最终结果。如果不通过，重新执行整个任务。

问题：代价太高。一个 6 步任务，如果第 2 步的结果有问题，但直到最后才发现，前 4 步的工作都白费了。而且，任务级评估只能告诉你"结果不对"，但不能告诉你"哪一步出了问题"，重新执行时无法针对性地改进。

**如果只有阶段级评估会怎样？**

每个阶段完成后立即评估。如果不通过，重试这个阶段。

这比只有任务级评估好，但还有一个问题：如果计划本身就是错误的呢？

比如，任务是"分析用户流失原因"，但计划的第一步是"查询用户注册数据"，而实际上应该先查询"用户最后活跃时间"。每个阶段都通过了评估（因为每个阶段都完成了计划要求的工作），但最终结果是错误的，因为计划方向就不对。

**计划评估的价值**

在执行任何步骤之前，先评估计划本身是否合理。这是最便宜的评估——在花费任何执行成本之前，就发现计划的问题。

计划评估可以发现：
- 步骤顺序不合理（比如在获取数据之前就开始分析）
- 遗漏了关键步骤（比如没有数据清洗步骤）
- 步骤目标与任务目标不一致
- 需要用户澄清的歧义（比如"分析销售数据"——是哪个时间段的？哪个地区的？）

**三层评估的协同**

三层评估形成了一个"早发现、早修复"的体系：

- 计划评估：在执行前发现计划级别的问题，代价最低
- 阶段评估：在每个阶段完成后发现阶段级别的问题，代价中等
- 任务评估：在所有步骤完成后发现任务级别的问题，代价最高但必要

### 11.2 评估报告的设计：LLM 判断恢复策略

`EvaluationReport` 不只包含"通过/不通过"，还包含 `recovery_action`——评估器推荐的恢复策略。

```python
@dataclass
class EvaluationReport:
    passed: bool
    feedback: str
    recovery_action: StageRecoveryAction | TaskRecoveryAction | None
    need_user_clarification: bool = False
    clarification_question: str = ""
```

`StageRecoveryAction` 有三种：
- `RETRY_SAME_STEP`：重试当前步骤（参数调整或工具选择问题）
- `REPLAN_THIS_STEP`：重新规划当前步骤（步骤目标理解有误）
- `REPLAN_FROM_THIS_STEP`：从当前步骤开始重新规划后续所有步骤（当前步骤的失败影响了后续步骤的前提）

**为什么让 LLM 判断恢复策略，而不是用规则引擎？**

规则引擎的思路是：根据错误类型决定恢复策略。比如，"工具调用失败 → 重试"，"结果格式错误 → 重新规划"。

这种方法的问题是：错误类型和恢复策略之间的关系非常复杂，很难用规则完整描述。

举几个例子：

**例子 1**：SQL 查询返回了空结果。这是"工具调用失败"吗？不是，工具执行成功了，只是结果为空。应该重试吗？不一定——可能是查询条件太严格，需要调整；也可能是数据确实不存在，需要告知用户。规则引擎很难区分这两种情况，但 LLM 可以根据上下文判断。

**例子 2**：阶段结果包含了正确的数据，但格式不符合要求（比如要求 JSON 但返回了 Markdown 表格）。规则引擎可能会判断为"格式错误 → 重新规划"，但实际上只需要重试并明确格式要求就够了。LLM 可以识别出这是格式问题而不是内容问题，推荐 `RETRY_SAME_STEP`。

**例子 3**：阶段结果在技术上是正确的，但与任务目标不符（比如任务要求分析"高价值用户"，但阶段结果分析了"所有用户"）。规则引擎无法识别这种语义层面的偏差，但 LLM 可以，并推荐 `REPLAN_THIS_STEP`。

LLM 的判断能力在这些复杂场景下远超任何规则引擎。

### 11.3 评估的成本与收益

每次评估都需要一次 LLM 调用，有 token 成本和延迟成本。这个成本是否值得？

**计划评估**：几乎总是值得的。计划评估的成本（一次 LLM 调用，约 500-1000 token）远低于执行一个错误计划的成本（多次 LLM 调用 + 工具调用）。

**阶段评估**：通常值得，但有例外。对于简单的、低风险的阶段（比如"查询数据库获取原始数据"），评估的价值相对较低，因为这类阶段的结果很容易验证（有数据就是成功，没数据就是失败）。

**任务评估**：总是值得的。这是最终的质量把关，确保交付给用户的结果是正确的。

**可配置的评估策略**

NanoAgent 支持通过配置控制评估行为：

```yaml
agent:
  enable_plan_evaluation: true      # 是否评估计划
  enable_stage_evaluation: true     # 是否评估阶段结果
  enable_task_evaluation: true      # 是否评估任务结果
  max_quality_retries: 2            # 任务级评估失败后的最大重试次数
```

对于对延迟敏感的场景，可以禁用阶段评估，只保留计划评估和任务评估。这会降低质量保障的粒度，但可以显著减少延迟。

### 11.4 评估提示词的设计

好的评估提示词需要解决两个对立的问题：**不能太宽松**（否则评估失去意义），**也不能太严格**（否则正确的结果也会被拒绝）。

**防止过于宽松**

评估提示词需要明确指定评估标准，而不是让 LLM 自由发挥。NanoAgent 的评估提示词包含：

- `task_goal`：任务的整体目标，让评估器知道这个阶段的结果需要服务于什么目的
- `output_constraints`：输出格式和内容的具体要求
- `step.key_results`：这个阶段应该产出的关键结果列表

有了这些具体标准，评估器不会因为"结果看起来不错"就通过，而是会检查结果是否满足所有具体要求。

**防止过于严格**

评估提示词需要明确说明：评估的是"结果是否满足要求"，而不是"结果是否完美"。

一个常见的问题是：评估器会因为结果"可以更好"而拒绝通过，即使结果已经满足了所有要求。这会导致无限重试循环。

NanoAgent 的评估提示词明确包含这样的指导："如果结果满足了所有关键要求，即使存在可以改进的地方，也应该通过评估。只有在结果明显不满足要求时，才应该拒绝。"

### 11.5 澄清机制

在计划评估阶段，评估器可能发现任务描述存在歧义，需要用户澄清。这时，`EvaluationReport` 会包含：

```python
need_user_clarification: bool = True
clarification_question: str = "请问您需要分析哪个时间段的销售数据？（例如：最近 30 天、本季度、本年度）"
```

**澄清的交互流程**

1. 计划评估返回 `need_user_clarification=True`
2. Pipeline 发布 `UserClarificationRequested` 事件，携带澄清问题
3. 用户界面展示澄清问题，等待用户回复
4. 用户回复后，Pipeline 收到 `UserClarificationReceived` 事件
5. 澄清内容被注入到任务上下文中，重新生成计划
6. 重新进行计划评估

这个流程确保了：当任务描述不够清晰时，Agent 不会盲目执行一个可能方向错误的计划，而是主动寻求用户的确认。

**澄清的边界**

澄清机制只在计划评估阶段触发，不在阶段执行过程中触发。这是一个有意的设计决策：一旦开始执行，就应该尽量自主完成，不频繁打断用户。

如果在执行过程中遇到无法自主解决的问题，Agent 会在阶段评估中标记失败，并在反馈中说明需要用户提供什么信息，而不是直接中断执行等待用户输入。

## 12. 知识与偏好：让 Agent 越用越聪明

### 12.1 两种记忆机制

NanoAgent 有两种独立的记忆机制，分别存储不同类型的信息。

**知识库（Knowledge）**：存储关于**世界**的事实性信息。

具体来说，知识库存储的是在任务执行过程中发现的、对未来任务有价值的信息：

- **数据库 Schema**：执行数据分析任务时，LLM 查询了数据库，发现了表结构。这个 Schema 信息对未来的数据分析任务很有价值，可以直接使用，不需要再次查询。
- **API 调用模式**：某个 API 的正确调用方式（参数格式、认证方式、常见错误处理）。
- **数据质量问题**：某个数据源存在的已知问题（比如某个字段有 NULL 值、某些记录的日期格式不一致）。
- **业务规则**：从任务执行中发现的业务规则（比如"VIP 用户的定义是消费金额超过 10000 元"）。

**偏好库（Preference）**：存储关于**用户**的行为偏好。

偏好库存储的是从用户的任务描述和反馈中提取的偏好信息：

- **输出格式偏好**：用户喜欢 Markdown 格式还是纯文本？喜欢详细的分析还是简洁的摘要？
- **语言偏好**：用户习惯用中文还是英文？技术术语用中文还是英文？
- **详细程度偏好**：用户希望看到执行过程的详细日志，还是只看最终结果？
- **工具使用偏好**：用户更喜欢用 Python 处理数据，还是用 SQL？

**两种记忆的使用方式**

知识库在任务开始时被加载，注入到任务上下文中，让 LLM 在推理时可以利用这些已知信息。

偏好库在任务开始时被查询，注入到系统提示中，影响 LLM 的整体行为风格。

### 12.2 异步学习：不影响当前任务

知识提取和偏好提取都是**异步**的——在任务完成后，在后台线程中执行，不阻塞当前任务的返回。

```python
# 任务完成后，异步提取知识和偏好
threading.Thread(
    target=self._knowledge_manager.extract_and_save,
    args=(task, result, self._llm_gateway),
    daemon=True,
).start()
```

**异步的代价**

异步学习意味着：当前任务执行过程中发现的知识，不会在当前任务中被使用。如果任务的第 3 步发现了数据库 Schema，这个信息会在任务完成后才被保存，第 4、5、6 步无法利用这个已保存的知识。

这是一个有意的权衡：**用学习延迟换取执行延迟的降低**。

如果同步提取知识（每个阶段完成后立即提取并保存），每个阶段都会增加一次 LLM 调用的延迟。对于一个 6 步任务，这意味着额外 6 次 LLM 调用，可能增加 30-60 秒的总延迟。

**是否有场景需要同步学习？**

有，但很少见。如果任务的某个阶段发现了关键信息，而后续阶段强烈依赖这个信息，同步学习会更好。

但在实践中，这种情况通常可以通过上下文传递解决：阶段 3 的结果会被放入上下文，阶段 4 可以直接从上下文中读取，不需要经过知识库。知识库的价值在于**跨任务**的信息传递，而不是同一任务内的信息传递。

### 12.3 语义检索：为什么向量搜索比关键词搜索更好

知识库使用向量搜索（ChromaDB）进行检索，而不是关键词搜索。

**关键词搜索的局限**

假设知识库中存储了这样一条知识：
> "用户表的主键是 user_id，类型为 VARCHAR(36)，存储 UUID 格式的字符串。"

如果用户的新任务是"统计活跃用户数量"，关键词搜索会查找"活跃用户"这个词，但知识库中没有这个词，搜索结果为空。

但实际上，这条关于用户表结构的知识对"统计活跃用户"任务是有价值的——知道主键是 `user_id` 可以帮助构造正确的 SQL 查询。

**向量搜索的优势**

向量搜索基于语义相似度，而不是词汇匹配。"统计活跃用户数量"和"用户表的主键是 user_id"在语义上是相关的（都涉及用户数据），向量搜索可以找到这种关联。

另一个例子：知识库中有"API 调用需要在 Header 中传入 Bearer Token"，新任务是"调用外部服务获取天气数据"。关键词搜索找不到匹配（没有"天气"这个词），但向量搜索可以识别出"调用外部服务"和"API 调用"的语义相关性。

### 12.4 知识提取的挑战

并不是所有任务执行过程中产生的信息都值得存储。好的知识需要满足几个条件：

**可复用性**：这个信息在未来的任务中会被用到吗？"用户表有 100 万条记录"可能是有价值的（影响查询策略），但"今天的查询返回了 42 条结果"通常没有复用价值。

**稳定性**：这个信息会随时间变化吗？数据库 Schema 相对稳定，值得存储。但"当前活跃用户数"每天都在变化，不适合存储为知识。

**准确性**：这个信息是确定的事实，还是 LLM 的推断？确定的事实（比如从数据库查询到的 Schema）值得存储，但 LLM 的推断（比如"这个字段可能是用户 ID"）不应该作为知识存储。

NanoAgent 使用 LLM 来判断哪些信息值得提取为知识。提取提示词明确要求 LLM 只提取"可复用的、稳定的、确定的"信息，过滤掉噪声。

**LLM 提取的局限性**

LLM 提取知识的质量取决于提示词的质量和 LLM 的判断能力。在实践中，LLM 有时会提取过于细节的信息（比如某次查询的具体结果），有时会遗漏重要的信息（比如数据质量问题）。

这是一个需要持续优化的地方。一个可能的改进方向是：让用户在任务完成后审查提取的知识，手动标记哪些值得保留，哪些应该删除。

### 12.5 偏好的衰减与更新

用户偏好会随时间变化。一个用户可能在早期喜欢详细的分析报告，但随着对系统的熟悉，开始偏好简洁的摘要。

**当前的处理方式**

NanoAgent 的偏好文件是一个追加写入的 JSONL 文件，每条记录包含 `created_at` 时间戳。当文件超过阈值（64KB）时，自动删除最旧的 20 条记录（`compact()` 方法）。

这是一个简单的"最近优先"策略：较新的偏好记录会保留，较旧的会被删除。这在一定程度上实现了偏好的自然衰减。

**局限性**

当前的实现没有显式的置信度分数或衰减机制。如果用户在 3 个月前表达了某个偏好，这个偏好和昨天表达的偏好在系统中有同等的权重（只要都在文件中）。

**未来改进方向**

1. **置信度分数**：根据偏好被观察到的频率和最近性，计算置信度分数。高置信度的偏好在提示词中占更重要的位置。

2. **显式衰减**：为每条偏好记录设置一个"有效期"，过期的偏好自动降权或删除。

3. **冲突检测**：当新的偏好与旧的偏好冲突时（比如用户之前喜欢详细报告，现在要求简洁），自动识别冲突并更新。

4. **用户反馈循环**：让用户可以显式地确认或否定系统推断的偏好，提高偏好的准确性。

## 13. 可观测性：生产系统的眼睛

### 13.1 三层可观测性

NanoAgent 的可观测性分三层：追踪（Tracing）、日志（Logging）、领域事件（Domain Events）。每一层解决不同的生产问题。

**追踪（Tracing）：诊断性能问题**

追踪记录了每个操作的开始时间、结束时间、状态和属性。它回答的问题是：**这个任务为什么这么慢？哪个步骤花了最多时间？**

具体的生产场景：用户反馈某个任务花了 15 分钟，但预期应该在 5 分钟内完成。通过追踪数据，可以快速定位：是哪个阶段特别慢？是 LLM 调用慢（提供商响应慢），还是工具执行慢（数据库查询慢），还是评估慢（评估 LLM 响应慢）？

**日志（Logging）：诊断逻辑问题**

日志记录了系统的运行状态和关键决策。它回答的问题是：**这个任务为什么失败了？系统做了什么决策？**

具体的生产场景：某个任务失败了，错误信息是"工具调用失败"。通过日志，可以看到：工具调用了什么参数？返回了什么错误？系统做了几次重试？最终是什么原因导致放弃？

**领域事件（Domain Events）：实时监控和集成**

领域事件是结构化的、类型化的事件，可以被订阅和处理。它回答的问题是：**系统现在在做什么？发生了什么重要的事情？**

具体的生产场景：
- **实时 UI 更新**：前端订阅 `StageExecutionStarted`、`StageExecutionSucceed` 等事件，实时更新进度条。
- **告警**：订阅 `TaskExecutionFailed` 事件，触发告警通知。
- **审计日志**：订阅所有事件，记录完整的任务执行历史，用于合规审计。

### 13.2 可观测性的设计原则：内建而非外加

NanoAgent 的可观测性是**内建**的，而不是事后添加的。

这意味着：每个关键操作在设计时就考虑了可观测性需求，追踪 Span、日志调用、事件发布都是代码的一部分，而不是通过 AOP 或装饰器事后注入的。

**事后添加可观测性的代价**

如果可观测性是事后添加的，通常会遇到这些问题：

- **信息不完整**：事后添加的日志往往缺少关键的上下文信息（比如 task_id、step_order），因为这些信息在添加日志时不容易获取。
- **覆盖不均匀**：开发者会在"感觉重要"的地方添加日志，但遗漏一些"看起来不重要但实际上关键"的地方。
- **性能影响难以控制**：事后添加的追踪可能在关键路径上引入不必要的开销。

内建可观测性的好处是：每个操作的可观测性需求在设计时就被考虑，信息完整、覆盖均匀、性能影响可控。

### 13.3 追踪的层次结构

NanoAgent 的追踪使用嵌套 Span 结构，形成一个层次树：

```
session (根 Span)
├── pipeline.analyze_task
├── pipeline.route_model
├── pipeline.make_plan
│   └── quality.evaluate_plan
├── pipeline.execute_stages
│   ├── stage.execute (step 1)
│   │   ├── reasoning.react_loop
│   │   │   ├── tool.execute.query_mysql_data
│   │   │   ├── tool.execute.run_python
│   │   │   └── tool.execute.run_python
│   │   └── quality.evaluate_stage_result
│   ├── stage.execute (step 2)
│   │   └── ...
│   └── quality.evaluate_task_result
└── knowledge.extract_and_save (后台)
```

**每个层次捕获的属性**

- `session`：task_id、user_id、task_description（长度）
- `pipeline.*`：task_id、plan_id、step_count
- `stage.execute`：step_id、step_order、start_reason
- `reasoning.react_loop`：iteration_count、tool_calls_count
- `tool.execute.*`：tool_name、argument_keys、success、error_code
- `quality.evaluate_*`：passed、feedback_length、recovery_action

这种层次结构让问题定位非常精确：如果某个任务慢，可以先看 `session` 级别的总时间，然后逐层下钻，找到具体是哪个 Span 耗时最长。

**追踪数据的存储**

追踪数据以 JSONL 格式存储在 `var/tracing/` 目录下，按小时分文件（`{YYYYMMDDHH}_trace.jsonl`）。每条记录是一个完整的 Span，包含 trace_id、span_id、parent_span_id，可以重建完整的调用树。

### 13.4 领域事件的设计

NanoAgent 定义了 30+ 个领域事件，覆盖了任务生命周期的所有关键节点。

**领域事件 vs 日志**

日志是给人看的，领域事件是给程序处理的。

日志的典型形式：
```
2024-01-15 10:23:45 INFO Stage execution started: step_order=2, goal="数据清洗"
```

领域事件的典型形式：
```python
StageExecutionStarted(
    task_id="task-123",
    metadata={"order": 2, "goal": "数据清洗"}
)
```

领域事件是结构化的、类型化的，可以被程序订阅和处理：

```python
event_bus.subscribe(StageExecutionStarted, lambda e: update_progress_bar(e.metadata["order"]))
event_bus.subscribe(TaskExecutionFailed, lambda e: send_alert(e.task_id, e.metadata["error"]))
```

**事件的设计原则**

每个事件都继承自 `DomainEvent`，包含 `task_id`、`user_id`、`content`（人类可读的描述）和 `metadata`（机器可读的结构化数据）。

`content` 字段是为了方便在 UI 上直接展示事件内容，不需要额外的格式化逻辑。`metadata` 字段包含事件的详细数据，供程序处理。

### 13.5 结构化日志的字段设计

NanoAgent 使用 zap 风格的结构化日志：

```python
self._logger.info(
    "Stage execution started",
    zap.any("task_id", task.id),
    zap.any("step_order", step.order),
    zap.any("step_goal", step.goal),
    zap.any("provider", current_provider),
)
```

**为什么结构化字段比字符串插值更好？**

字符串插值的日志：
```
INFO Stage execution started: task_id=abc123, step_order=2, goal=数据清洗, provider=deepseek
```

结构化字段的日志（JSON 格式）：
```json
{
  "level": "INFO",
  "message": "Stage execution started",
  "task_id": "abc123",
  "step_order": 2,
  "step_goal": "数据清洗",
  "provider": "deepseek",
  "timestamp": "2024-01-15T10:23:45Z"
}
```

结构化日志的优势：

1. **可查询**：可以用 `task_id = "abc123"` 精确过滤，而不是用正则表达式解析字符串。
2. **可聚合**：可以统计"每个 provider 的平均执行时间"，因为 `provider` 是一个独立的字段，而不是嵌在字符串里。
3. **类型安全**：`step_order` 是整数，不是字符串，可以做数值比较和排序。
4. **工具友好**：ELK Stack、Datadog、Grafana Loki 等日志聚合工具都原生支持 JSON 格式，可以直接建立索引和仪表盘。

在生产环境中，当你需要回答"过去 24 小时内，使用 deepseek 提供商的任务平均执行了多少步骤？"这样的问题时，结构化日志让这个查询变得简单，而字符串日志需要复杂的正则解析。

## 14. 设计总结：几个关键决策的取舍

### 14.1 不可变领域对象：正确性优先于性能

NanoAgent 的核心领域对象（`Task`、`Plan`、`PlanStep` 等）使用 `@dataclass(frozen=True)` 定义，是不可变的。

**考虑的替代方案**：可变对象（普通 dataclass 或 dict）。

**选择不可变对象的原因**：

在多线程环境中（Agent 线程 + 用户线程），可变对象需要锁保护，否则会有竞态条件。不可变对象天然线程安全，不需要锁。

更重要的是，不可变对象让代码更容易推理。当你看到一个 `Task` 对象被传入某个函数，你可以确定这个函数不会修改 `Task` 的状态。这大幅降低了调试的难度。

**已知的代价**：

不可变对象意味着每次"更新"都需要创建新对象。比如，当任务分析完成，需要更新 `Task` 的 `task_goal` 字段，需要创建一个新的 `Task` 对象：

```python
task = Task(
    id=task.id,
    task_goal=new_goal,  # 更新的字段
    # ... 其他字段保持不变
)
```

这会产生额外的内存分配和 GC 压力。但在实践中，`Task` 对象的更新频率很低（每个任务只更新几次），这个代价完全可以接受。

**什么时候这个代价会变得不可接受？**

如果需要高频更新领域对象（比如每次工具调用都更新某个计数器），不可变对象的代价就会显现。在这种情况下，可以考虑把高频更新的状态分离出来，用可变对象管理，而核心领域对象保持不可变。

### 14.2 三级循环：复杂性换可靠性

**考虑的替代方案**：单一的 ReAct 循环，没有阶段划分。

**选择三级循环的原因**：

单一 ReAct 循环的问题是：当任务失败时，无法精确定位失败点，也无法做到精确恢复。只能从头重来。

三级循环（任务级 → 阶段级 → 推理级）让失败处理更精细：推理级失败（工具调用失败）在推理循环内处理；阶段级失败（阶段结果不合格）在阶段循环内处理；任务级失败（最终结果不合格）在任务循环内处理。

**已知的代价**：

三级循环增加了代码复杂度。`StageExecutor` 的实现是整个框架中最复杂的部分，需要处理各种失败模式和恢复策略的组合。

### 14.3 LLM 驱动的决策：灵活性优先于可预测性

**考虑的替代方案**：规则引擎驱动的决策（比如"工具失败 3 次 → 切换提供商"）。

**选择 LLM 驱动的原因**：

规则引擎无法处理语义层面的判断（比如"这个阶段结果是否满足任务目标"）。LLM 可以理解上下文，做出更智能的决策。

**已知的代价**：

LLM 的决策不是完全可预测的。相同的输入可能产生不同的输出（由于温度参数）。这让系统的行为更难以测试和调试。

在实践中，通过降低评估 LLM 的温度（接近 0），可以提高决策的一致性，但无法完全消除不确定性。

### 14.4 多提供商支持：可靠性优先于简单性

**考虑的替代方案**：只支持单一 LLM 提供商。

**选择多提供商的原因**：

单一提供商意味着单点故障。当提供商出现问题（过载、维护、API 变更），整个系统就不可用了。

多提供商支持让系统在提供商故障时自动切换，提高了整体可用性。

**已知的代价**：

不同提供商的 API 格式、能力、价格都不同。维护多个提供商的适配器增加了代码量和测试复杂度。

### 14.5 检查点机制：持久性优先于简单性

**考虑的替代方案**：不实现检查点，任务失败就从头重来。

**选择检查点的原因**：

对于长任务（30 分钟以上），从头重来的代价太高（时间 + API 成本）。检查点让系统在任何时间点崩溃后都能恢复，大幅提高了长任务的成功率。

**已知的代价**：

检查点实现增加了代码复杂度，特别是状态序列化和恢复逻辑。pickle 序列化的版本兼容性问题也是一个持续的维护负担。

### 14.6 并发模型：双线程 vs async/await

NanoAgent 使用双线程模型：用户线程（处理用户输入）和 Agent 线程（执行任务）。两个线程通过 `threading.Event` 和消息队列通信。

**为什么不用 async/await？**

async/await 是 Python 中处理并发的现代方式，看起来更优雅。但它有一个重要的限制：**整个调用链必须是异步的**。

NanoAgent 的工具执行（特别是 `RunPythonTool` 使用 `multiprocessing`，`ShellTool` 使用 `subprocess`）本质上是同步的阻塞操作。把这些操作包装成异步的，需要使用 `asyncio.run_in_executor()`，增加了复杂度，而且性能提升有限（因为瓶颈在 LLM API 调用，不在 Python 代码本身）。

双线程模型更简单直接：Agent 线程同步执行所有操作，用户线程通过消息队列发送控制信号（取消、指导、澄清）。

**`threading.Event` 的使用**

当 Agent 需要等待用户澄清时，使用 `threading.Event` 阻塞 Agent 线程，直到用户线程设置事件：

```python
# Agent 线程
clarification_event = threading.Event()
event_bus.publish(UserClarificationRequested(...))
clarification_event.wait()  # 阻塞，等待用户回复
clarification = self._driver.get_clarification()

# 用户线程
def on_user_clarification(content: str):
    driver.set_clarification(content)
    clarification_event.set()  # 唤醒 Agent 线程
```

这种模式简单、可靠，不需要复杂的异步协调。

### 14.7 提示词模板化：可维护性优先于简单性

NanoAgent 使用 Jinja2 模板管理所有提示词，模板文件存储在 `config/prompts/` 目录下。

**为什么不把提示词直接写在代码里？**

代码内嵌提示词的问题：

1. **修改需要改代码**：调整提示词需要修改 Python 文件，触发代码审查流程，增加了迭代成本。
2. **版本管理不清晰**：提示词的变更混在代码变更中，很难单独追踪提示词的演化历史。
3. **非技术人员无法参与**：产品经理或领域专家可能需要调整提示词，但他们不应该需要修改 Python 代码。

Jinja2 模板的好处：

1. **提示词和代码分离**：修改提示词不需要改代码，可以独立迭代。
2. **模板复用**：多个提示词可以共享公共片段（比如系统角色描述）。
3. **动态内容注入**：通过模板变量，可以把任务信息、计划信息等动态内容注入提示词，而不需要字符串拼接。

**版本控制的含义**

提示词文件和代码文件都在 Git 中管理。这意味着提示词的每次修改都有完整的历史记录，可以回滚，可以做 A/B 测试（不同分支使用不同的提示词）。

### 14.8 不可变领域对象的性能代价

前面提到了不可变对象的代价是额外的内存分配。让我们更具体地分析这个代价。

在 NanoAgent 的典型执行流程中，`Task` 对象会被更新几次：
- 任务分析完成后，更新 `task_goal`、`task_type` 等字段
- 计划生成完成后，可能更新 `output_constraints`
- 每次阶段完成后，不需要更新 `Task`（阶段结果存储在 `Stage` 对象中）

总共大约 2-3 次更新，每次创建一个新的 `Task` 对象（约 1KB 内存）。这个代价完全可以忽略不计。

**什么时候不可变对象的代价会变得显著？**

如果需要在每次工具调用后更新某个领域对象（比如记录工具调用次数），不可变对象的代价就会显现。在这种情况下，NanoAgent 的做法是：把高频更新的状态（比如迭代计数器）放在可变的 `Stage` 对象中，而不是不可变的 `Task` 或 `Plan` 对象中。

### 14.9 单体框架 vs 微服务

NanoAgent 是一个单进程框架，所有组件（LLM 网关、工具执行、上下文管理、评估等）都在同一个进程中运行。

**单体框架的优势**

- **低延迟**：组件间通信是函数调用，没有网络开销。
- **简单部署**：一个进程，一个配置文件，不需要服务发现和负载均衡。
- **调试方便**：所有状态在同一个进程中，可以用标准的 Python 调试工具。

**单体框架的局限**

- **扩展性**：如果需要同时处理大量并发任务，单进程的 GIL 会成为瓶颈（虽然 LLM API 调用是 I/O 密集型，GIL 影响相对较小）。
- **隔离性**：一个任务的崩溃可能影响其他任务（虽然 NanoAgent 的错误处理设计尽量避免这种情况）。

**什么时候需要拆分成微服务？**

当以下情况出现时，可以考虑拆分：

1. **工具执行需要独立扩展**：如果某些工具（比如 Python 执行）需要大量计算资源，可以把工具执行服务独立部署，按需扩展。
2. **多租户隔离**：如果需要严格隔离不同用户的任务（比如 SaaS 场景），可以把每个用户的 Agent 运行在独立的进程或容器中。
3. **LLM 网关独立化**：如果多个应用需要共享 LLM 配额管理和熔断器状态，可以把 LLM 网关独立部署为一个服务。

对于大多数使用场景，单体框架已经足够。过早的微服务化会增加不必要的复杂度。

## 结语

写完这篇文章，回头看整个 NanoAgent 的开发历程，有几点感受想分享。

### 最出乎意料的复杂性

开始动手之前，我以为最难的部分是 LLM 的提示词工程——如何让 LLM 生成高质量的计划，如何让 ReAct 循环稳定运行。

但实际上，**上下文管理才是最难的工程问题**。

`tool_use` 和 `tool_result` 必须成对出现这个约束，在截断、回滚、检查点恢复等操作中，会以各种意想不到的方式被违反。我花了大量时间在 `_repair_context()` 管道上，处理各种边缘情况：截断后孤立的 `tool_result`、回滚后连续的同角色消息、检查点恢复后第一条消息不是 `user` 角色……

每次以为修好了，又会发现新的边缘情况。最终的五步修复管道是在真实任务执行中一个一个 bug 积累出来的，不是一开始就设计好的。

另一个出乎意料的复杂性是**多提供商的差异**。我以为不同 LLM 提供商的 API 大同小异，适配起来应该很快。但实际上，每个提供商都有自己的怪癖：Anthropic 的 `tool_use` 消息格式和 OpenAI 不同，DeepSeek 的错误响应格式和 Qwen 不同，MiniMax 的流式响应格式又是另一套……每个提供商都需要仔细测试，处理各种边缘情况。

### 如果重来一次，我会做什么不同

**第一，更早引入类型系统**。NanoAgent 从一开始就使用了全量类型注解，但在早期开发中，有些地方用了 `Any` 类型作为临时方案，后来这些 `Any` 变成了技术债，需要花时间清理。如果重来，我会从第一行代码就坚持严格的类型注解，不留 `Any` 的余地。

**第二，更早设计可观测性**。虽然 NanoAgent 的可观测性是内建的，但在早期开发中，我花了很多时间在没有足够日志的情况下调试问题。如果重来，我会在写第一个功能模块时就把追踪和日志框架搭好，让后续开发从一开始就有完整的可观测性。

**第三，更早写集成测试**。单元测试很容易写，但 Agent 系统的很多 bug 只在集成场景下才会出现（比如上下文管理的 bug 只在多步骤任务中才会触发）。如果重来，我会更早投入时间写端到端的集成测试，用真实的 LLM 调用（或者高质量的 mock）测试完整的任务执行流程。

**第四，更保守地使用 pickle**。检查点序列化用 pickle 是一个快速但不够健壮的选择。版本兼容性问题在开发过程中已经让我头疼了几次。如果重来，我会从一开始就设计一个基于 JSON 的序列化方案，虽然实现更复杂，但长期维护成本更低。

### 路线图上的下一步

**流式输出的改进**：当前的流式支持是基础的，只是把 LLM 的流式响应转发给用户。更好的流式支持应该包括：工具执行的实时进度更新、阶段切换的流式通知、上下文压缩时的用户提示。

**更好的摘要机制**：当前的上下文截断策略是简单地删除旧消息。更好的方案是在删除之前生成摘要，保留关键信息。这需要一个高质量的摘要提示词，以及对摘要质量的评估机制。

**多 Agent 协调**：当前 NanoAgent 是单 Agent 框架。对于某些复杂任务，多个专门化的 Agent 协作可能比单个通用 Agent 更有效。比如，一个专门负责数据查询的 Agent，一个专门负责数据分析的 Agent，一个专门负责报告生成的 Agent，由一个协调 Agent 统筹调度。

**更智能的工具选择**：当前的工具过滤基于静态的相关性评分。更好的方案是动态的工具选择：根据任务执行的实时状态，动态调整可用工具集。比如，当某个工具连续失败时，自动降低它的优先级；当某个工具在类似任务中表现良好时，自动提高它的优先级。

**知识库的向量化**：当前的知识库使用文件存储，检索是全量加载后过滤。对于大型知识库，这会变得很慢。引入向量数据库（ChromaDB 已经在依赖中了），用语义搜索替代全量加载，可以大幅提高检索效率。

### 写给读者

如果你正在构建自己的 Agent 系统，希望这篇文章能给你一些有用的参考。

几个实践建议：

**从可靠性开始设计**。不要等到系统跑起来了再考虑可靠性。在设计阶段就问自己：这个地方如果失败了，系统会怎么处理？每一个可能失败的地方，都应该有对应的恢复策略。

**把上下文管理当作一等公民**。上下文管理是 Agent 系统中最容易被低估的工程问题。`tool_use`/`tool_result` 配对、角色顺序约束、token 预算管理——这些问题在 demo 中不会出现，但在生产中会频繁发生。提前设计好上下文管理，会省去大量的调试时间。

**可观测性是投资，不是成本**。在 Agent 系统中，LLM 的行为是不完全可预测的，问题可能以各种意想不到的方式出现。完善的可观测性让你能够快速定位问题，而不是在黑盒中盲目调试。

**小步迭代，真实任务验证**。Agent 系统的很多问题只在真实任务中才会暴露。不要在 demo 任务上过度优化，尽早用真实的、复杂的任务来验证系统的可靠性。
