# 从零设计一个生产级 LLM Agent 框架

> ThinkingAgent 是一个轻量级但生产就绪的 Python LLM Agent 框架，支持多 LLM Provider、复杂任务编排、自动故障恢复和长任务断点续跑。本文记录了我在构建 ThinkingAgent 过程中的核心系统设计思考

## 1. 战略规划

最开始只有一个模糊的目标：从0到1做一个能自主分析/规划/执行/验收，帮用户解决通用性问题的个人智能助手。脑海中虽然有很多关于LLM Agent技术领域的零星想法，但没有整合成一个结构化的思考体系。所以我面临的第一个问题是面对这个模糊的目标，在执行层面上的规划问题

### 1.1 明确需求与目标

- 需要结合LLM推理和外部工具调用的任务
- 长周期，多步骤，具有一定复杂性的任务

### 1.2 明确执行顺序

[画一个图，四层，基础能力域(任务意图识别，任务分解，推理轨迹编排，工具调用)，可靠执行域(模型路由与熔断，断点续跑，执行评估，预算管理，上下文窗口管理，系统容错与降级机制，可观测性处理)，安全执行域(工具沙箱，调用检查，权限管理，风险识别)，智能执行域(知识数据飞轮，工具能力飞轮，推理轨迹纠偏)]

首先我将Agent的能力分成了如上图的四个层次，每一个层次都是不同的领域问题，都可以独立深入和演进，同时这四个层次从下到上也代表了Agent能力的进阶路径 。这种分层让我可以根据自己的时间安排，决定在哪些领域可以多花一些精力，哪些少一点，哪些必须做，哪些留给未来做

### 1.3 明确设计原则

传统没营养的软件设计原则不提了

**“基础能力”与“能力约束”同时设计**

LLM Agent是一个典型的Pipeline系统，在pipeline执行的每一个环节都有可能失败

**每一个可能失败的地方，都要有对应的恢复策略；每一个恢复策略，都要有代价意识。**

这句话包含两个关键点：

第一，"每一个可能失败的地方"——这要求在设计阶段就系统性地思考所有可能的失败模式，而不是等到出问题了再打补丁。

第二，"代价意识"——不是所有失败都需要最激进的恢复策略。如果只是工具参数写错了，重试一次就够了，没必要重新生成整个计划。代价意识让系统在可靠性和效率之间找到平衡

## 2. 系统架构设计

### 2.1 架构分层

ThinkingAgent 采用五层垂直分离架构：

```
┌─────────────────────────────────────────────────────────────┐
│                      应用入口层 (Entry)                       │
│                           CLI | Web
├─────────────────────────────────────────────────────────────┤
│                    应用编排层 (Application Orchestration)                   │
│        AgentService| Pipeline  ←→  PipelineDriver       │
├─────────────────────────────────────────────────────────────┤
│                    Agent 模型层 (Models)                      │
│  Analyzer │ Planner │ StageExecutor │ ReasoningManager | ComponentAssembler │
│  ContextManager │ ModelSelector │ QualityEvaluator           │
│  CheckpointManager │ KnowledgeManager │ PersonalityManager   │
├─────────────────────────────────────────────────────────────┤
│                    基础能力层 (Infrastructure)                │
│   LLMGateway │ ToolRegistry │ RepositoryAdaptor │ EventBus | PromptTemplateEngine   │ConfigReader
├─────────────────────────────────────────────────────────────┤
│                    基础设施层 (Infra)                         │
│   Storage │ Cache │ HTTP Client │ Logger |Tracer|Metrics
└─────────────────────────────────────────────────────────────┘
```

### 2.2 架构设计核心思路

一开始我把LLM Agent当成是一种典型的Pipeline数据流系统，因此用数据流系统的设计方法来建模。但随着系统的复杂性和规模上升，加入新feature越来越麻烦，修BUG的次数越来越多，原来的设计好的聚合边界开始模糊，变化传播范围开始失去约束，某些聚合有成为上帝对象的风险，某些又贫血的要死。它相比于传统的数据流系统多了一个重要特征，就是强依赖LLM Driven的动态决策，如果只实现基础能力域，但是开始叠加可靠执行域的实施，对架构的重新审视已经刻不容缓。

这里采用的方法是结合DDD领域建模+数据流系统设计的方式

1. 基于数据流如何流动和变化，提出系统关键的业务事实
2. 编排这些业务事实发生的时间先后顺序
3. 推导产生这些业务事实的Command和相关约束Policy
4. 根据业务事实/Command/Policy抽聚合
5. 对每一个聚合抽出聚合根，约定好聚合边界，以及确定与外部交互的契约

随着功能的逐步增加，这一套思考过程进行了N轮，产生了目前的架构，它肯定不是最好的，但是能满足我现在的需要

### 2.4 领域支撑设计

#### 2.4.1 Pipeline 是唯一的"上帝视角"

一个用户提交一个任务后，ThinkingAgent需要自主地去完成这个任务。在这个过程中涉及上面分层架构里介绍的所有实体的配合。为了不让依赖变成难以迭代和维护的网状，Pipeline作为中央协调者成为这个星形拓扑的唯一汇合点。

抽象出Pipeline对象有三个关键动机：

- 执行和解决用户任务需要串联和协调各个关键聚合根的动作顺序
- 所有实体需要有干净的依赖关系
- 未来如果ThinkingAgent需要支持多session任务的并发处理，Pipeline会成为推理执行流的数据流隔离单元，确保执行上下文的独立性

虽然Pipeline是中央协调者，但不代表其他聚合之间一点依赖没有。Pipeline解决的是Agent软件架构全局性的依赖问题，当问题限定到一个非常明确，容易控制的局部领域，聚合之间是可以有直接依赖的。比如ContextManager这个推理上下文管理器就需要依赖上下文裁剪器和token用量预估器来解决窗口太大超过模型限制的问题

#### 2.4.2 ComponentAssembler：依赖注入的统一入口

所有聚合根，关键实体的创建都是通过 `ComponentAssembler` 统一构建的，这不只是为了屏蔽对象创建的细节，更重要的是：

**测试替换**：测试时可以注入 mock 组件，不需要修改业务代码。比如，测试 Pipeline 的恢复逻辑时，可以注入一个总是返回失败的 mock QualityEvaluator，而不需要真正调用 LLM。

**配置集中**：这种系统的配置参数会非常多，我需要在一个收口的地方管理所有配置，进而调整整个系统的行为，而不是让配置散落在代码的各个角落。

**依赖可见**：组件的依赖关系在`ComponentAssembler` 中一目了然，不会出现隐式依赖。当你看到 `build_stage_executor()` 需要传入 `reasoning_manager`、`context_manager`、`quality_evaluator` 等参数时，你立刻就知道 StageExecutor 依赖哪些组件

**生命周期管理**：`ComponentAssembler` 控制组件的创建顺序，确保依赖关系正确初始化。比如，LLMGateway 必须在 ReasoningManager 之前创建，因为 ReasoningManager 依赖 LLMGateway

#### 2.4.3 PipelineDriver：用户与 Agent 的消息桥梁

`PipelineDriver` 是一个容易被忽视但非常有必要的设计，引入这个实体主要是解决两方面问题

- 支持预定义的产品能力

  一个好的LLMAgent必然需要能够"与人协同"，比如Agent要求用户权限放过，信息澄清，二次确认，或者用户想要主动进行的任务引导等等。因此ThinkingAgent需要在任务执行过程中与用户的各种指令交互，`PipelineDriver`对外暴露和管理与Entry层交互的异步消息队列，收发与传递用户和Agent之间交互的消息

- 技术上的防腐层

  为了保障Pipeline等Agent内部实体契约和实现的稳定，Driver层负责用户消息和Agent标准Command互转，以及杂七杂八的业务逻辑

#### 2.4.4 EventBus事件总线：解耦通知

ThinkingAgent使用事件驱动的方式处理可以异步化的操作，在系统设计阶段已经定义好了完整的系统领域事件，这些领域事件都会被`Pipeline`对象通过 `EventBus` 发布，这意味着：

- `Pipeline`不需要知道谁在监听阶段完成事件
- Checkpoint保存，用户偏好提取，可复用知识提取，监控系统、审计日志等都可以独立订阅感兴趣的事件
- 添加新的监听者不需要修改任何现有代码

系统定义了 15+ 个领域事件，覆盖从任务分析开始到最终交付的完整生命周期：`TaskAnalysisStarted`、`PlanGenerateSucceed`、`StageExecutionStarted`、`ToolCallStarted`、`ToolCallResultProduced`、`TaskExecutionSucceed` 等。

这些事件不只是用于通知，它们也是系统状态的完整记录。通过订阅所有事件，可以重建任务执行的完整时间线，这对于调试和审计非常有价值。

## 3. 基础能力层

### 3.1 推理框架

#### 3.1.2 推理模式：Plan-and-Execute Agent with Self-Reflection

【需要2个图】

ThinkingAgent首先会根据任务分析阶段的输出，对任务进行复杂度分解并制定执行计划，这一步其实在应用Plan-and-Execute，ThinkingAgent Execute的就是计划里的每个步骤(Stage)，Execute的过程采用ReAct模式，当Execute成功返回后又会追加一个Self-Reflection。当Self-Refelction发现不满足交付条件，可能RePlan或者Retry Execute

**以Plan-and-Execute为骨架，以ReAct为血肉，以Reflection为进化驱动力的混合式智能体**

#### 3.1.3 系统控制流骨架：三段式工作循环

ThinkingAgent 采用了如下图所示的三级嵌套的控制流循环

```
┌─────────────────────────────────────────────────────────────┐
│  任务级循环 (Task Level)                                      │
│      
│  ┌───────────────────────────────────────────────────────┐  │
│  │  步骤级循环 (Stage Level)                               │  │
│  │  
│  │  ┌─────────────────────────────────────────────────┐  │  │
│  │  │  推理级循环 (Reasoning Level)                    │  │  │
│  │  │  Thought → Action → Observation → ...           │  │  │
│  │  └─────────────────────────────────────────────────┘  │  │
│  └───────────────────────────────────────────────────────┘  │
└─────────────────────────────────────────────────────────────┘
```

这样的设计基于三个不同维度的出发点：

- 适配ThinkingAgent的推理模式
- 有利于简化复杂控制流的决策深度
- 有利于可靠性体系设计

##### 3.1.3.1 推理级循环：ReAct 的实现

最内层的推理循环实现了 ReAct 范式。每次迭代的完整流程：

**第一步：轮询用户指令（非阻塞）**

在每次推理迭代开始时，系统会非阻塞地检查是否有用户指令（取消、引导等）。这个检查是非阻塞的，如果没有指令，立即继续执行，不会等待。

这个设计让用户可以在任务执行过程中随时干预：发送取消指令立即停止任务，发送引导指令（比如"注意，数据库中的日期格式是 YYYY-MM-DD"）会被注入到上下文中，影响后续的推理。

**第二步：构建上下文窗口**

调用 `ContextManager.get_context_window(provider_name)`，这个方法会：

- 对消息序列进行修复（五步修复管道）
- 根据 token 预算进行截断（如果需要）
- 返回可以直接发给 LLM 的 `ContextWindow` 对象

**第三步：调用 LLM 获取决策**

通过 `ReasoningManager.reason_once()` 调用 LLM，得到一个 `NextDecision` 对象，包含决策类型和相关数据。

**第四步：根据决策类型分支处理**

- `FINAL_ANSWER`：阶段完成，调用 `stage.complete(answer)`，退出循环
- `TOOL_CALL`：执行工具，把工具结果作为 observation 注入上下文，继续循环
- `CLARIFICATION_NEEDED`：向用户请求澄清，等待用户回复后继续
- `PAUSED`：等待用户发送 RESUME 指令后继续
- `CONTINUE`：LLM 有中间思考但还没有最终答案，注入 assistant 消息，继续循环

这个循环最多运行 `max_iterations`（默认 60）次，超出后触发模型切换，而不是直接失败。这是因为迭代次数超限通常意味着 LLM 陷入了某种循环，切换到不同的提供商可能会打破这个循环。

### 3.2. 任务分析：让 Agent 真正理解任务

#### 3.2.1 为什么需要任务分析？

大多数 Agent 框架收到用户输入后，直接开始规划和执行。ThinkingAgent 在这之前多了一个关键步骤：**任务分析（Task Analysis）**。

这个步骤的价值在于：**把一个模糊的自然语言请求，转化为一个结构化的、机器可处理的任务描述**。

为什么这很重要？考虑这样一个用户请求："帮我分析一下上个季度的销售情况"。

这个请求包含很多模糊性：

- "上个季度"是哪个季度？需要根据当前日期计算
- "销售情况"包括哪些维度？总销售额、同比增长、分产品线、分地区？
- 数据在哪里？数据库？Excel 文件？
- 输出格式是什么？文字报告？图表？表格？

如果直接把这个模糊的请求交给 Planner，生成的计划很可能不够精准，执行过程中会遇到各种问题。任务分析的作用就是在执行之前，把这些模糊性尽可能消除。

#### 3.2.2 分析产出的信息

`Analyzer` 通过 LLM 从用户输入中提取以下信息：

**任务语义层面**：

`task_type` 标识任务的类型，比如"数据分析"、"代码生成"、"信息检索"、"文档处理"等。这个字段直接影响模型路由——不同类型的任务适合不同的 LLM 提供商。

`intent` 捕捉用户的真实意图，有时和字面意思不同。比如，"帮我看看这段代码有没有问题"的真实意图可能是"代码审查并给出改进建议"，而不只是"找 bug"。

`task_goal` 描述任务的最终目标，用于在整个执行过程中保持方向一致。每个阶段的执行提示词都会包含 `task_goal`，确保 LLM 不会在细节中迷失方向。

`entities` 提取任务中涉及的关键实体，并进行规范化处理。比如：

- "上周五" → "2026-05-15"（具体日期）
- "AAPL" → "AAPL"（股票代码，已是标准格式）
- "销售数据库" → 需要进一步确认具体的数据库名称

实体规范化很重要，因为 LLM 在后续步骤中需要使用这些实体，规范化后的格式更不容易出错。

**执行约束层面**：

`action_constraints` 捕捉用户的行为约束，比如"不要修改原始文件"、"只查询不写入"、"不要调用外部 API"等。这些约束会注入到每个阶段的执行提示词中，确保 Agent 不会做出用户不希望的操作。

`output_constraints` 描述输出格式要求，比如"输出 Markdown 格式"、"结果要包含数据来源"、"不超过 500 字"等。这些约束在质量评估时作为评估标准之一。

`risks` 识别任务的潜在风险，比如"数据可能过时"、"成本可能超支"、"任务范围可能蔓延"等。这些风险信息会注入到计划生成提示词中，让 Planner 在生成计划时考虑这些风险。

**工具匹配层面**：

`tool_matches` 是任务分析中最有工程价值的输出之一。Analyzer 对每个可用工具计算相关性评分（0.5-1.0），低于 0.5 的工具直接排除，高于阈值（默认 0.65）的工具才会出现在 LLM 的工具列表中。

这个评分不是简单的关键词匹配，而是语义层面的相关性判断。比如，对于"分析 Excel 销售数据"这个任务，`excel` 工具的评分会很高，`flight_search` 工具的评分会很低（接近 0），`run_python` 工具的评分会中等（因为 Python 也可以处理 Excel，但不如专用工具）。

**路由提示层面**：

`routing_hints` 是给模型路由器的结构化提示，包括：

- `required_capability_tags`：任务需要的能力标签（如 "code"、"tool_use"、"long_context"）
- `estimated_context_tokens`：预估的上下文 token 数（用于过滤上下文窗口不够大的提供商）
- `latency_sensitive`：是否对延迟敏感（影响提供商选择）
- `cost_sensitive`：是否对成本敏感（影响提供商选择）

#### 3.2.3 分析结果如何影响后续流程

任务分析的结果不只是给 Planner 看的，它贯穿整个执行流程：

**影响模型路由**：`routing_hints` 直接输入到 `CapabilityMatchStrategy` 的评分算法中，影响哪个 LLM 提供商被选为主选。

**影响工具过滤**：`tool_matches` 中的评分决定向 LLM 暴露哪些工具。这个过滤在计划生成后还会再做一次——Planner 在生成计划时也会对工具重新评分（`planner_score`），最终取两次评分的最大值与阈值比较。

**影响计划生成**：`entities`、`constraints`、`risks` 都会注入到 Planner 的提示词中，帮助生成更精准的计划。比如，如果 `risks` 中包含"数据可能过时"，Planner 可能会在计划中加入"验证数据时效性"的步骤。

**影响阶段执行**：`task_goal` 和 `intent` 注入每个阶段的提示词，保持执行方向一致。这防止了一种常见问题：LLM 在执行某个具体步骤时，忘记了整体任务的目标，做出了局部正确但全局错误的决策。

**影响质量评估**：`output_constraints` 作为评估标准之一。如果用户要求"输出 Markdown 格式"，但最终结果是纯文本，质量评估会标记为不通过。

#### 3.2.4 知识注入

任务分析后进行知识注入

任务分析阶段还会从两个外部来源加载信息：

**历史知识**：从向量数据库中检索与当前任务语义相似的历史知识条目。比如，如果之前执行过类似的数据分析任务，相关的数据库 Schema、常用查询模式、数据质量问题等会被检索出来，注入到当前任务的上下文中。

这个机制的价值在于：Agent 不需要每次都从零开始探索。如果之前已经发现了某个数据库的 Schema，下次执行类似任务时可以直接使用，不需要再次查询。

### 3.3 提示词工程

#### 3.3.1 基于模板提示词管理

ThinkingAgent 使用 Jinja2 模板管理所有提示词，模板文件存储在 `config/prompts/` 目录下。

**为什么不把提示词直接写在代码里？**

代码内嵌提示词的问题：

1. **修改需要改代码**：调整提示词需要修改 Python 文件，触发代码审查流程，增加了迭代成本。
2. **版本管理不清晰**：提示词的变更混在代码变更中，很难单独追踪提示词的演化历史。
3. **非技术人员无法参与**：产品经理或领域专家可能需要调整提示词，但他们不应该需要修改 Python 代码。

Jinja2 模板的好处：

1. **提示词和代码分离**：修改提示词不需要改代码，可以独立迭代。
2. **模板复用**：多个提示词可以共享公共片段（比如系统角色描述）。
3. **动态内容注入**：通过模板变量，可以把任务信息、计划信息等动态内容注入提示词，而不需要字符串拼接。

**版本控制的含义**

提示词文件和代码文件都在 Git 中管理。这意味着提示词的每次修改都有完整的历史记录，可以回滚，可以做 A/B 测试（不同分支使用不同的提示词）。

**工具选择的优先级规则**（first match wins）：

```
简单数学/单函数 → calculator
多步数据处理/numpy/pandas → run_python
纯文本/CSV 文件 → file
Excel 文件 → excel（先用 inspect 检查布局）

网络事实/近期事件 → search
```

这个优先级规则解决了一个常见问题：LLM 在面对多个可用工具时，往往会选择"万能"工具（如 run_python）而不是最合适的专用工具。明确的优先级规则引导 LLM 做出更精准的工具选择。

比如，对于"计算 sqrt(144)"这个简单任务，如果没有优先级规则，LLM 可能会选择 `run_python`（写一段 Python 代码来计算）。但实际上，`calculator` 工具更合适——它更轻量，不需要启动 Python 解释器，也不需要处理代码执行的安全问题。

### 3.4 检查点机制：长任务的生命线

#### 3.4.1 问题场景：第 25 分钟的崩溃

想象这样一个场景：你让 Agent 帮你分析一份复杂的销售数据报告。任务包含 6 个步骤：连接数据库、清洗数据、计算各维度指标、生成可视化图表、撰写分析报告、导出最终文件。整个任务预计需要 30 分钟，调用 LLM 约 40 次，工具调用约 60 次。

任务跑到第 25 分钟，正在执行第 5 步"撰写分析报告"。这一步已经完成了 80%，LLM 正在生成最后一段结论。突然，网络抖动，LLM API 返回了一个 503 错误，重试三次后仍然失败。

如果没有检查点机制，你面对的是：

**时间损失**：25 分钟的执行时间归零，需要从头重来。

**金钱损失**：这才是更让人心痛的部分。40 次 LLM 调用，按 GPT-4 的价格估算，大约花费了 2-3 美元。这些钱就这么打水漂了。如果你用的是 Claude Opus，损失可能更大。更糟糕的是，重跑一次还要再花同样的钱。

**用户体验损失**：用户等了 25 分钟，看到的是一个错误信息。他们不知道任务执行到哪里了，不知道哪些步骤已经完成，不知道是否需要重新提交任务。这种不确定性比单纯的等待更让人沮丧。

**为什么 Agent 任务特别脆弱？**

普通软件任务失败了，通常可以快速重试，因为每次执行的代价很低（毫秒级，几乎零成本）。但 Agent 任务有三个特点让它特别脆弱：

第一，**执行时间长**。一个复杂的 Agent 任务可能需要几分钟到几十分钟，期间任何一个环节出问题都会导致整体失败。执行时间越长，遇到问题的概率越高。

第二，**调用成本高**。每次 LLM 调用都有真实的 API 费用。一个 30 分钟的任务可能花费几美元，从头重来意味着双倍成本。

第三，**状态不可重现**。Agent 任务的中间状态往往是不可重现的——第 3 步生成的数据分析结果，第 4 步的图表，这些都是 LLM 在特定上下文下生成的，重跑不一定得到完全相同的结果。

检查点机制就是为了解决这个问题：**让长任务在任何时间点崩溃后，都能从最近的成功节点继续，而不是从头开始**。

#### 3.4.2 保存时机的设计：为什么是"评估通过后"

检查点的保存时机是一个关键设计决策。有几种选择：

**方案 A：每次工具调用后保存**

最细粒度的方案。每次工具执行完毕，立即保存检查点。

问题：工具调用非常频繁，一个阶段可能有 10-20 次工具调用。每次都保存意味着大量的磁盘 I/O，而且大多数中间状态并没有保存价值——一个阶段执行到一半的状态，恢复后也无法直接继续，还是需要重新执行这个阶段。

**方案 B：每次 LLM 推理后保存**

比方案 A 稍粗一些，但问题类似。LLM 推理的中间状态（比如"正在思考下一步用什么工具"）没有独立的恢复价值。

**方案 C：每个阶段完成后保存（不管质量如何）**

每当一个阶段的 ReAct 循环结束，LLM 给出了最终答案，就保存检查点。

问题：这个阶段的结果可能是错误的。如果我们保存了一个质量不合格的阶段结果，恢复后继续执行，后续阶段会基于这个错误结果继续，最终产出的任务结果也会是错误的。

**方案 D（ThinkingAgent 的选择）：每个阶段通过质量评估后保存**

只有当阶段结果通过了 `QualityEvaluator` 的评估，才保存检查点。

这个设计的核心洞察是：**检查点保存的是"已验证的进度"，而不是"已完成的工作"**。

"已完成"和"已验证"是两回事。一个阶段可能已经完成了（LLM 给出了答案），但答案是错误的（评估不通过）。如果保存了这个未验证的状态，恢复后继续执行，就是在错误的基础上继续构建，最终结果必然有问题。

只保存通过评估的阶段，确保了每个检查点都是一个"已知良好"的状态。从这个状态恢复，后续执行可以安全地依赖之前阶段的结果。

**保存时机的代码体现**：

```python
# 在 pipeline._execute_stages() 中
for step in plan.step_list[start_step_index:]:
    result = self._stage_executor.execute(step, task)
    
    # 只有阶段成功完成（包括通过评估），才保存检查点
    if result.success:
        CheckpointManager.save_async(
            CheckpointData(
                completed_step_index=step.order - 1,
                # ... 其他状态
            ),
            task_name=task.task_goal[:30],
        )
```

注意 `save_async`——检查点保存是异步的，在后台线程执行，不阻塞主执行流程。这是一个重要的性能优化：检查点保存涉及序列化和磁盘 I/O，如果同步执行，会增加每个阶段的延迟。

#### 3.4.3 保存内容的完整性：每一个字段都有理由

`CheckpointData` 包含以下字段，每一个都有其存在的理由：

```python
@dataclass
class CheckpointData:
    task_id: TaskId
    user_id: UserId
    task_description: str          # 原始任务描述
    task: Task                     # 完整的 Task 对象（含分析结果）
    plan: Plan                     # 完整的执行计划
    completed_step_index: int      # 已完成的最后一步索引（0-based）
    conversation_history: list[LLMMessage]  # 完整对话历史
    tool_schemas: list[dict]       # 过滤后的工具 Schema
    model_selector_state: ModelSelectorState  # 模型路由状态（含熔断器）
    task_output_constraints: str   # 输出约束
    task_goal: str                 # 任务目标
    task_intent: str               # 任务意图
    task_recovery_feedback: str    # 上次任务级恢复的反馈
```

**为什么要保存 `conversation_history`？**

这是最显而易见的——对话历史是 LLM 推理的上下文。没有它，恢复后的 LLM 不知道之前做了什么，会重新开始。

但有一个细节值得注意：保存的是 `conversation_history`（完整历史），而不是 `ctx_window`（当前活跃上下文）。这是因为恢复时需要重建完整的上下文状态，包括已经被截断的历史消息。

**为什么要保存 `tool_schemas`？**

直觉上，工具 Schema 是静态的，可以在恢复时重新生成。但实际上，ThinkingAgent 在执行前会根据任务特征过滤工具（只保留相关工具），这个过滤结果是动态的。

如果恢复时重新过滤，可能得到不同的工具集（比如任务分析的随机性导致不同的过滤结果）。这会导致恢复后的执行与原始执行使用不同的工具，破坏了执行的一致性。

保存过滤后的工具 Schema，确保恢复后使用完全相同的工具集。

**为什么要保存 `model_selector_state`（含熔断器状态）？**

这是最容易被忽视的字段，但也是最重要的之一。

`ModelSelectorState` 包含了熔断器的状态：哪些提供商当前处于熔断状态，熔断计数是多少。

如果不保存这个状态，恢复后熔断器会重置为初始状态。这意味着：如果某个提供商在执行前 5 步时频繁失败，已经被熔断了，恢复后熔断器重置，系统会再次尝试这个不稳定的提供商，可能再次触发失败。

保存熔断器状态，让恢复后的系统"记住"之前遇到的提供商问题，继续使用已经验证可靠的提供商。

**为什么要保存 `task_recovery_feedback`？**

这个字段记录了上一次任务级评估失败时的反馈信息。

场景：任务执行完所有步骤，但任务级评估不通过，评估器给出了反馈"结果缺少对异常数据的处理"。系统决定重新规划并重新执行。在重新执行过程中，如果某个阶段通过了评估，保存检查点时需要把这个反馈也保存进去。

为什么？因为如果这次重新执行又在某个阶段崩溃了，从检查点恢复时，需要知道"这次执行是在修复什么问题"。没有这个反馈，恢复后的执行可能忘记了需要处理异常数据，再次产出不合格的结果。

### 3.5 工具系统：保持简单而强大

#### 3.5.1 工具过滤：两遍打分的设计

ThinkingAgent 在执行任务前，会对所有可用工具进行过滤，只把相关工具的 Schema 放入 LLM 的上下文。这个过滤过程使用了两遍打分机制。

**为什么需要过滤工具？**

工具 Schema 会占用 token。如果系统有 20 个工具，把所有工具的 Schema 都放入上下文，可能消耗 2000-3000 个 token。对于简单任务，大多数工具是不相关的，这些 token 是浪费。

更重要的是，无关工具会干扰 LLM 的决策。当 LLM 面对 20 个工具时，它需要从中选择合适的工具，无关工具增加了选择的复杂度，可能导致 LLM 选错工具。

**第一遍：Analyzer 打分（`match_score`）**

任务分析阶段，`TaskAnalyzer` 会对每个工具进行相关性评分。这个评分基于任务描述和工具描述的语义相似度：这个工具对完成这个任务有多大帮助？

Analyzer 的视角是**任务整体**：它看的是整个任务描述，评估工具对整个任务的相关性。

**第二遍：Planner 打分（`planner_score`）**

计划生成阶段，`Planner` 在生成执行计划时，会对每个工具再次打分。这个评分基于计划的具体步骤：这个工具在执行计划的某个具体步骤时会被用到吗？

Planner 的视角是**执行细节**：它看的是具体的执行步骤，评估工具在实际执行中的使用可能性。

**两遍打分捕获不同的信息**

举一个具体例子：假设任务是"分析销售数据并生成报告"，系统有 `query_mysql_data`、`run_python`、`shell`、`travel_guide` 四个工具。

- `travel_guide`：Analyzer 打分 0.1（与销售分析无关），Planner 打分 0.1。两遍都低，过滤掉。
- `query_mysql_data`：Analyzer 打分 0.9（销售数据在数据库里），Planner 打分 0.9（计划第一步就是查询数据库）。两遍都高，保留。
- `run_python`：Analyzer 打分 0.7（数据分析可能需要 Python），Planner 打分 0.8（计划第二步是数据处理，用 Python）。保留。
- `shell`：Analyzer 打分 0.4（可能用到，但不确定），Planner 打分 0.2（计划里没有需要 shell 的步骤）。

对于 `shell` 这个工具，Analyzer 给了中等分（任务层面看起来可能有用），但 Planner 给了低分（具体计划里用不到）。最终取两者的最大值 0.4，低于阈值 0.65，过滤掉。

这就是两遍打分的价值：Analyzer 可能对某些工具过于乐观（"这个任务可能会用到"），Planner 的具体计划视角可以纠正这种过度乐观。反过来，Planner 可能对某些工具过于保守（计划里没有明确提到），Analyzer 的整体视角可以补充。

**过滤阈值**：默认 0.65，可通过配置调整。取两个分数的最大值，只要有一个分数超过阈值，工具就会被保留

## 4. 可靠性体系建设

*一个本质问题*：LLM Agent 执行复杂任务时，失败是常态，不是异常。工具调用可能失败，LLM 可能给出错误的推理，计划可能不合理，LLM Provider API可能不稳定。**最关键问题不是"如何避免失败"，而是"失败后如何以最小代价恢复"**

可靠性这种东西最麻烦的就是它无处不在，而因为大模型的原因，这个问题更复杂了。比如你可能看到系统没有任何显示的异常和报错，但推理轨迹就是偏离目标，或者推理就是陷入死循环。所有曾经其他系统面临的可靠性问题Agent要cover，而大模型引发新的可靠性问题，LLM Agent同样必须对应的处理手段。

### 4.1 可靠性设计思维导图

**先分层**

Task Level —— 关注Task交付质量的可靠，检查手段：主动检测，下层反馈，主动检测是结合Task的交付结果，对照Task维度信息进行评测,，恢复手段是基于Feedback重新Retry原有计划，重新制定执行计划并执行，下层反馈硬错误 给用户输出错误信息

Stage Level —— 关注Stage执行结果的可靠，检查手段：下层反馈有模型切换，硬错误。主动纠偏：对Stage执行结果进行质量评测，恢复手段是基于

Reasoning Level —— 下层反馈：硬错误+模型切换， 无主动检测

LLM Gateway Level —— 模型降级，带jitter的backoff重试，LLM回复schema本地修复(JSON格式，步骤需要的重要key-value都存在，修复成合法JSON即可)，下层反馈各模型API适配自己的错误

Tool Level —— 检测手段： 调用前检查(工具存在性检查，调用权限检查，行为权限检查，入参检查(必填参数检查，参数值类型检查))        恢复手段：带jitter的backoff重试 + 连续同类型工具调用过多插入引导prompt + 部分工具降级的替代工具 + 工具错误融合到推理轨迹，让LLM继续推理

上下文 Level —— 推理轨迹 （1）格式正确 （2）窗口大小（3）符合token预算 （4）语义单元完整 （5）推理过程信息尽量不失真

代价递增的四档策略

这是整个恢复机制中设计最精细的部分。当某个阶段的执行结果不达标时，系统有四档恢复策略，代价从低到高：

```
RETRY_SAME_STEP    → 最低代价：丢弃当前阶段上下文，原地重试
REPLAN_THIS_STEP   → 低代价：重新生成当前步骤的计划，重试
REPLAN_FROM_HERE   → 中代价：重新生成当前及后续所有步骤，重试
REPLAN_ALL         → 最高代价：重置全部上下文，重新生成整个计划
```

**为什么要有这四档而不是直接 REPLAN_ALL？**

因为代价是真实存在的。每次重规划都需要调用 LLM，消耗 token，增加延迟。如果只是当前步骤的执行方式有问题，没必要推翻整个计划。代价递增的策略确保系统总是先尝试最便宜的恢复方式。

让我们用一个具体例子来说明：

假设任务是"分析销售数据并生成报告"，计划有 5 个步骤：

1. 连接数据库，查询销售数据
2. 清洗和预处理数据
3. 计算关键指标
4. 生成可视化图表
5. 撰写分析报告

如果第 3 步（计算关键指标）的结果不正确，应该怎么恢复？

- 如果是因为 SQL 查询写错了（比如 GROUP BY 字段选错了），`RETRY_SAME_STEP` 就够了——LLM 看到错误结果后会修正查询
- 如果是因为第 3 步的计划描述不够清晰，导致 LLM 不知道要计算哪些指标，`REPLAN_THIS_STEP` 更合适——重新生成第 3 步的计划，明确指定要计算的指标
- 如果是因为第 2 步的数据清洗有问题，导致第 3 步的输入数据就是错的，`REPLAN_FROM_HERE` 更合适——从第 2 步开始重新规划
- 如果是因为整个计划的分析思路就不对，`REPLAN_ALL` 才是正确选择

自动升级机制：防止死循环

有一个微妙但重要的设计：**恢复策略会自动升级**。

如果同一步骤连续 2 次 `RETRY_SAME_STEP` 都失败了，系统会自动将恢复策略升级到 `REPLAN_THIS_STEP`。这防止了一种常见的死循环：LLM 每次都建议"重试"，但问题根本不是执行问题，而是计划本身有缺陷。

```python
# 升级链：代价从低到高
escalation = {
    RETRY_SAME_STEP  → REPLAN_THIS_STEP,
    REPLAN_THIS_STEP → REPLAN_FROM_HERE,
    REPLAN_FROM_HERE → REPLAN_ALL,
}
# 触发条件：同一步骤连续 2 次相同失败
if same_failure_count >= 2:
    action = escalate(action)
```

这个机制背后的逻辑是：如果同样的恢复策略连续失败两次，说明这个策略不足以解决问题，需要升级到更激进的策略。这是一种自适应的恢复机制，不需要人工干预。

同时，系统还设置了全局上限：每步最多 `max_replan_stage_retries`（默认 3）次恢复，全局最多 `max_total_replan_count`（默认 8）次重规划。这防止了系统在一个无法解决的问题上无限循环。

#### 4.2.3 低置信度时的处理

任务分析的结果包含一个 `confidence` 字段（0-1），表示 Analyzer 对分析结果的置信度。当置信度低于阈值时，系统会触发澄清流程：

`implicit_needs` 字段包含 Analyzer 认为需要澄清的问题列表。这些问题会通过 `UserClarificationRequested` 事件发布，等待用户回复后再继续执行。

这个设计避免了一种常见问题：在任务描述模糊的情况下，Agent 基于错误的假设执行了很长时间，最后发现方向完全错了。提前澄清虽然增加了一点交互成本，但避免了更大的浪费。

#### 4.2.4 不可变领域对象：防御性设计

核心领域对象（`Task`、`Plan`、`PlanStep`）被声明为不可变，这是一个防御性设计决策。

在并发环境中，可变的共享状态是 bug 的温床。如果 `Task` 对象是可变的，那么在 Pipeline 读取 `task.task_goal` 的同时，另一个线程可能正在修改它，导致难以复现的竞态条件。

不可变对象从根本上消除了这类问题：一旦创建，对象的状态就不会改变。需要"修改"时，创建一个新对象。这种模式在函数式编程中很常见，在并发场景下尤为有价值

### 4.3. 上下文管理：最难的工程问题

如果说三级循环是 ThinkingAgent 最核心的**架构设计**，那么上下文管理就是最核心的**工程挑战**。

在实际开发中，上下文管理踩的坑比任何其他模块都多

#### 4.3.1 问题的复杂性来源

LLM 的上下文窗口是有限的，但 Agent 执行复杂任务时产生的消息可能非常多：

- 每次 LLM 推理产生一条 assistant 消息
- 每次工具调用产生一条 tool 消息（包含工具参数）
- 每次工具返回产生一条 tool_result 消息（包含执行结果）
- 多步骤任务可能有几十甚至上百条消息

当消息总量超过上下文窗口时，必须截断。但截断不是简单地删掉最旧的消息，因为：

**约束 1：tool_use 和 tool_result 必须成对出现**

如果删掉了 tool_use 但保留了 tool_result，大多数 LLM API 会报错。反过来，如果删掉了 tool_result 但保留了 tool_use，LLM 会认为工具调用还没有完成，可能重复调用同一个工具。

**约束 2：第一条消息必须是 user 角色**

这是所有主流 LLM API（OpenAI、Anthropic、Qwen 等）的要求。如果截断后第一条消息变成了 assistant 或 tool，API 会报错。

**约束 3：不能有连续的同角色消息**

Anthropic API 明确拒绝连续的 user 或 assistant 消息。这在截断后很容易出现：如果删掉了某条 assistant 消息，可能导致两条 user 消息相邻。

**约束 4：阶段边界必须可追踪**

当某个阶段执行失败需要回滚时，需要精确删除该阶段产生的所有消息，而不影响其他阶段的消息。如果阶段边界信息丢失，就无法做到精确回滚。

**约束 5：检查点恢复后的一致性**

从检查点恢复时，需要把保存的对话历史重新加载到上下文中。加载后的消息序列必须满足上述所有约束，否则恢复后的第一次 LLM 调用就会失败。

这五个约束相互交织，使得上下文管理成为整个系统中最复杂的工程问题。

#### 4.3.2 双缓冲设计：ctx_window 与 history 分离

`ContextManager` 维护两个独立的消息列表：

```
_ctx_window  ← 当前活跃上下文（可增删）
_history     ← 完整追加历史（只增不删）
```

**为什么要分离？**

`_ctx_window` 是发给 LLM 的实际内容，需要根据 token 预算动态调整。`_history` 是完整的审计记录，永远不删除。

这两个列表的用途完全不同：

`_ctx_window` 用于：

- 构建发给 LLM 的请求（`get_context_window()`）
- 阶段回滚（删除失败阶段的消息）
- 检查点保存（保存当前活跃上下文）

`_history` 用于：

- 知识提取（从完整对话历史中提取有价值的信息）
- 偏好学习（从完整对话历史中学习用户偏好）
- 审计和调试（完整记录任务执行过程）

当阶段执行失败需要回滚时，我们从 `_ctx_window` 中删除该阶段的消息，但 `_history` 保持完整。这意味着即使某个阶段被回滚了，它的执行记录仍然保留在历史中，可以用于后续的分析和学习。

**内存代价**：双缓冲设计的代价是内存占用翻倍。对于长任务，`_history` 可能积累大量消息。但这个代价是值得的——完整的历史记录对于知识提取和调试来说是不可替代的。

#### 4.3.3 上下文修复：五步自动修复

每次调用 `get_context_window()` 时，都会运行一个五步修复管道，确保发给 LLM 的消息序列是合法的：

```
原始消息列表
    │
    ▼ Step 1: _drop_leading_tool_results()
    │  删除出现在任何 tool_use 之前的孤立 tool_result 消息
    │  （这种情况在截断后可能出现：截断删掉了 tool_use，但保留了 tool_result）
    │
    ▼ Step 2: _ensure_first_message_is_user()
    │  删除开头的非 user 消息，直到第一条 user 消息
    │  （所有主流 LLM API 要求对话以 user 开始）
    │
    ▼ Step 3: _repair_tool_pairs()
    │  检查每个 tool_use 是否有对应的 tool_result
    │  对于没有 result 的 tool_use，注入合成的错误结果
    │  对于没有对应 tool_use 的 tool_result，直接删除
    │
    ▼ Step 4: _drop_trailing_tool_use()
    │  删除消息列表末尾的 tool_use 消息（没有对应 result）
    │  （Step 3 的安全网，防止边缘情况）
    │
    ▼ Step 5: _merge_consecutive_same_role()
       合并相邻的同角色消息（tool_use 和 tool_result 除外）
       （Anthropic API 拒绝连续的 user 或 assistant 消息）
```

这个修复管道是防御性编程的典型案例。每一步都在处理一种可能出现的非法状态，确保无论上游发生什么（截断、阶段回滚、检查点恢复），发给 LLM 的消息序列始终合法。

**Step 3 的细节**：`_repair_tool_pairs()` 是最复杂的一步。它需要处理多工具调用的情况（一个 assistant 消息可能包含多个 tool_use），以及工具调用结果乱序的情况（某些提供商的响应中，tool_result 的顺序可能与 tool_use 不一致）。

实现上，它维护一个 `pending` 字典，key 是 tool_call_id，value 是对应的 stage_index。遍历消息列表时：

- 遇到 tool_use：把所有 call_id 加入 pending
- 遇到 tool_result：从 pending 中移除对应的 call_id
- 遇到下一个 assistant 消息或列表结束：对 pending 中剩余的 call_id，注入合成的错误结果

**Step 5 的细节**：合并连续同角色消息时，需要特别处理 tool_use 和 tool_result 消息——这两种消息不能合并，因为它们携带结构化的元数据（call_id、tool_name 等），合并会破坏这些元数据。

#### 4.3.4 Token 预算管理：角色分配制

上下文窗口的 token 预算不是平均分配的，而是按角色分配：

```
总预算 (total_budget)
    │
    ├─ 预留区 (reserved_tokens = total_budget × reserve_ratio)
    │       用于 LLM 响应输出 + 未来可能的摘要调用
    │       这部分不能被输入消息占用
    │
    └─ 可用区 (available_tokens = total_budget - reserved_tokens)
            按角色比例分配：
            ├─ system 消息：ratio_system × available
            ├─ user 消息：ratio_user × available
            ├─ assistant 消息：ratio_assistant × available
            └─ tool 消息：ratio_tool × available
```

**为什么要预留区？**

如果输入消息把 token 预算用满了，LLM 就没有空间输出响应了。预留区确保 LLM 始终有足够的 token 来生成完整的回复。

这个问题在实践中比想象的更常见。当任务执行到后期，上下文中积累了大量的工具调用结果（有些工具的输出可能很长），很容易把 token 预算用满。如果没有预留区，LLM 的响应会被截断，导致工具调用参数不完整，进而导致工具执行失败。

**为什么要按角色分配而不是总量控制？**

不同角色的消息有不同的重要性和压缩空间：

- system 消息包含关键指令（ReAct 系统提示、阶段提示），不应该被截断
- user 消息包含任务描述和用户指令，重要性高
- assistant 消息包含 LLM 的推理过程，可以适当压缩（保留最近的，删除较早的）
- tool 消息（工具执行结果）往往很长，但可以大幅压缩（只保留关键信息）

按角色分配让截断策略更精细：当 token 超限时，优先压缩 tool 消息，其次是较早的 assistant 消息，最后才考虑 user 消息。

##### 4.3.5.2 渐进式压缩处理

当消息总量超过预算时，`ContextTruncator` 执行截断。截断策略的核心原则是：

**保留最近的推理轨迹，压缩或删除较早的历史**。

这个原则背后的逻辑是：LLM 在推理时，最近的上下文比较早的上下文更重要。当前步骤的推理需要看到最近几次工具调用的结果，但不一定需要看到第一步的详细执行过程。

**具体截断流程**：

1. **计算当前 token 使用量**：对 `_ctx_window` 中的所有消息进行 token 估算（使用字符/token 比例快速估算，不调用 tokenizer）

2. **确定需要删除的 token 数**：`需要删除 = 当前使用量 - 可用预算`

3. **从头部开始删除**：按时间顺序，从最旧的消息开始删除，直到释放足够的 token 空间

4. **保护 tool_use/tool_result 配对**：不拆散工具调用对，整对删除或整对保留。如果删除一条 tool_use 消息，必须同时删除对应的所有 tool_result 消息

5. **摘要替代（可选）**：对于被删除的历史段落，可以选择调用 LLM 生成一段摘要，注入到上下文中，保留关键信息而不是完全丢弃

6. **截断后修复**：截断完成后，重新运行 `_repair_context()` 管道，确保结果合法

**摘要注入的权衡**：

摘要注入需要额外的 LLM 调用，增加延迟和成本。但对于长任务，早期阶段的关键信息（比如第一步发现的数据库 Schema、第二步清洗数据时发现的数据质量问题）如果完全丢失，可能导致后续步骤出错。

这是一个延迟/成本 vs 准确性的权衡，通过配置控制是否启用。对于对准确性要求高的任务，建议启用摘要注入；对于对延迟要求高的任务，可以禁用。

**Token 估算的精度问题**：

精确的 token 计数需要调用 tokenizer，这有一定的计算成本。ThinkingAgent 使用字符/token 比例（默认 3.5 字符/token）进行快速估算，在大多数情况下误差在 10% 以内。

对于不同的提供商，这个比例可能不同（中文文本的比例通常更低，因为一个汉字可能对应 2-3 个 token）。系统支持按提供商配置不同的估算比例，也支持接入真实的 tokenizer 进行精确计数

#### 4.5.3 连续同质化调用限制

在 ReAct 推理循环中，有一种特殊的失败模式：**工具调用死循环**。

**死循环的典型样子**

想象 LLM 在执行"查询用户数据"这个步骤：

```
第 1 次迭代：
  LLM 思考：我需要查询用户表
  LLM 调用：query_mysql_data(statement="SELECT * FROM users")
  工具返回：错误，表 'users' 不存在

第 2 次迭代：
  LLM 思考：查询失败了，我再试一次
  LLM 调用：query_mysql_data(statement="SELECT * FROM users")
  工具返回：错误，表 'users' 不存在

第 3 次迭代：
  LLM 思考：可能是大小写问题
  LLM 调用：query_mysql_data(statement="SELECT * FROM Users")
  工具返回：错误，表 'Users' 不存在

第 4 次迭代：
  LLM 思考：我再试一次原来的查询
  LLM 调用：query_mysql_data(statement="SELECT * FROM users")
  工具返回：错误，表 'users' 不存在
  ...
```

LLM 陷入了一个循环：它知道查询失败了，但不知道如何解决，于是反复尝试相同或相似的查询。这个循环可以持续很多次，消耗大量的 token 和时间，却没有任何进展。

**ThinkingAgent 的解决方案**

`StageExecutor` 维护一个连续工具调用计数器。每次 LLM 调用工具，计数器加 1；每次 LLM 给出非工具调用的响应（比如最终答案），计数器重置为 0。

当计数器超过阈值（默认 10 次），系统不会直接终止执行，而是**向上下文注入一条干预消息**：

```
[系统提示] 你已经连续调用工具 10 次。请停下来思考：
1. 当前的工具调用策略是否有效？
2. 是否需要换一种方法？
3. 如果问题无法通过工具解决，请直接给出你目前能提供的最佳答案。
```

**为什么注入消息而不是直接终止？**

直接终止会导致阶段失败，触发重试或重新规划，代价很高。

注入消息给了 LLM 一个"自我反思"的机会。很多时候，LLM 在看到这条提示后，会意识到自己陷入了循环，然后换一种策略（比如先查询数据库 Schema，再构造正确的查询）。

这种"软干预"比"硬终止"更优雅，也更符合 Agent 的自主性原则：我们不是强制终止 LLM 的行为，而是给它一个信号，让它自己做出调整。

#### 4.5.4 LLM-Driven修复

### 4.6. 质量评估：让 Agent 自我审视

#### 4.6.1 三个层次的评估：为什么不能少

ThinkingAgent 的质量评估分三个层次：计划评估、阶段结果评估、任务结果评估。这三个层次不是冗余的，每个层次解决不同的问题。

**如果只有任务级评估会怎样？**

任务执行完所有步骤后，评估最终结果。如果不通过，重新执行整个任务。

问题：代价太高。一个 6 步任务，如果第 2 步的结果有问题，但直到最后才发现，前 4 步的工作都白费了。而且，任务级评估只能告诉你"结果不对"，但不能告诉你"哪一步出了问题"，重新执行时无法针对性地改进。

**如果只有阶段级评估会怎样？**

每个阶段完成后立即评估。如果不通过，重试这个阶段。

这比只有任务级评估好，但还有一个问题：如果计划本身就是错误的呢？

比如，任务是"分析用户流失原因"，但计划的第一步是"查询用户注册数据"，而实际上应该先查询"用户最后活跃时间"。每个阶段都通过了评估（因为每个阶段都完成了计划要求的工作），但最终结果是错误的，因为计划方向就不对。

**计划评估的价值**

在执行任何步骤之前，先评估计划本身是否合理。这是最便宜的评估——在花费任何执行成本之前，就发现计划的问题。

计划评估可以发现：

- 步骤顺序不合理（比如在获取数据之前就开始分析）
- 遗漏了关键步骤（比如没有数据清洗步骤）
- 步骤目标与任务目标不一致
- 需要用户澄清的歧义（比如"分析销售数据"——是哪个时间段的？哪个地区的？）

**三层评估的协同**

三层评估形成了一个"早发现、早修复"的体系：

- 计划评估：在执行前发现计划级别的问题，代价最低
- 阶段评估：在每个阶段完成后发现阶段级别的问题，代价中等
- 任务评估：在所有步骤完成后发现任务级别的问题，代价最高但必要

#### 4.6.2 LLM 判断恢复策略

`EvaluationReport` 不只包含"通过/不通过"，还包含 `recovery_action`——评估器推荐的恢复策略。

```python
@dataclass
class EvaluationReport:
    passed: bool
    feedback: str
    recovery_action: StageRecoveryAction | TaskRecoveryAction | None
    need_user_clarification: bool = False
    clarification_question: str = ""
```

`StageRecoveryAction` 有三种：

- `RETRY_SAME_STEP`：重试当前步骤（参数调整或工具选择问题）
- `REPLAN_THIS_STEP`：重新规划当前步骤（步骤目标理解有误）
- `REPLAN_FROM_THIS_STEP`：从当前步骤开始重新规划后续所有步骤（当前步骤的失败影响了后续步骤的前提）

**为什么让 LLM 判断恢复策略，而不是用规则引擎？**

规则引擎的思路是：根据错误类型决定恢复策略。比如，"工具调用失败 → 重试"，"结果格式错误 → 重新规划"。

这种方法的问题是：错误类型和恢复策略之间的关系非常复杂，很难用规则完整描述。

举几个例子：

**例子 1**：SQL 查询返回了空结果。这是"工具调用失败"吗？不是，工具执行成功了，只是结果为空。应该重试吗？不一定——可能是查询条件太严格，需要调整；也可能是数据确实不存在，需要告知用户。规则引擎很难区分这两种情况，但 LLM 可以根据上下文判断。

**例子 2**：阶段结果包含了正确的数据，但格式不符合要求（比如要求 JSON 但返回了 Markdown 表格）。规则引擎可能会判断为"格式错误 → 重新规划"，但实际上只需要重试并明确格式要求就够了。LLM 可以识别出这是格式问题而不是内容问题，推荐 `RETRY_SAME_STEP`。

**例子 3**：阶段结果在技术上是正确的，但与任务目标不符（比如任务要求分析"高价值用户"，但阶段结果分析了"所有用户"）。规则引擎无法识别这种语义层面的偏差，但 LLM 可以，并推荐 `REPLAN_THIS_STEP`。

LLM 的判断能力在这些复杂场景下远超任何规则引擎。

#### 4.6.3 评估的成本与收益

每次评估都需要一次 LLM 调用，有 token 成本和延迟成本。这个成本是否值得？

**计划评估**：几乎总是值得的。计划评估的成本（一次 LLM 调用，约 500-1000 token）远低于执行一个错误计划的成本（多次 LLM 调用 + 工具调用）。

**阶段评估**：通常值得，但有例外。对于简单的、低风险的阶段（比如"查询数据库获取原始数据"），评估的价值相对较低，因为这类阶段的结果很容易验证（有数据就是成功，没数据就是失败）。

**任务评估**：总是值得的。这是最终的质量把关，确保交付给用户的结果是正确的。

**可配置的评估策略**

ThinkingAgent 支持通过配置控制评估行为：

```yaml
agent:
  enable_plan_evaluation: true      # 是否评估计划
  enable_stage_evaluation: true     # 是否评估阶段结果
  enable_task_evaluation: true      # 是否评估任务结果
  max_quality_retries: 2            # 任务级评估失败后的最大重试次数
```

对于对延迟敏感的场景，可以禁用阶段评估，只保留计划评估和任务评估。这会降低质量保障的粒度，但可以显著减少延迟

### 4.7 智能模型路由：不只是轮询

#### 4.7.1 问题背景

当你有多个 LLM 提供商可用时，如何选择最合适的那个？

最简单的方案是轮询或随机选择，但这忽略了一个重要事实：**不同的 LLM 在不同类型的任务上有显著的能力差异**。Claude 在长文本理解和代码生成上表现出色，DeepSeek 在数学推理上有优势，Qwen 对中文任务更友好，MiniMax 在某些特定场景下成本更低。

如果你有一个需要复杂数学推理的任务，把它发给一个不擅长数学的提供商，结果质量会明显下降，甚至需要多次重试才能得到正确答案。这不只是质量问题，也是成本问题——错误的提供商选择会导致更多的重试，消耗更多的 token。

ThinkingAgent 的模型路由系统试图解决这个问题：**根据任务特征，自动选择最合适的提供商**。

#### 4.7.2 CapabilityMatchStrategy：多信号加权评分

默认的路由策略 `CapabilityMatchStrategy` 对每个候选提供商计算一个综合评分，综合考虑多个维度的匹配程度：

**正向信号**（任务与提供商能力的匹配程度）：

| 信号                           | 权重  | 设计意图           |
| ------------------------------ | ----- | ------------------ |
| 任务类型精确匹配提供商偏好类型 | +8    | 最强信号，直接命中 |
| 所需能力标签命中提供商标签     | +5/个 | 能力维度匹配       |
| 认知复杂度层级覆盖             | +3    | 提供商能处理该难度 |
| 场景描述 Jaccard 相似度匹配    | +2/个 | 语义层面的场景匹配 |
| 需要工具调用且提供商支持       | +3    | 工具能力匹配       |
| API 稳定性加成                 | +0~+5 | 可靠性权重         |

**负向惩罚**（风险和约束）：

| 惩罚条件                        | 权重 | 设计意图       |
| ------------------------------- | ---- | -------------- |
| 预估 token 数超过上下文窗口 70% | -5   | 防止上下文溢出 |
| 延迟敏感但提供商响应慢          | -3   | SLO 保障       |
| 成本敏感但提供商价格高          | -3   | 成本约束       |
| 用户偏好低成本/低延迟           | -2   | 软约束         |

评分最高的提供商成为主选，其余按分数排序形成备用链。

**为什么用 Jaccard 相似度而不是向量相似度？**

Jaccard 相似度计算的是两个词集合的交集比例，计算成本极低（不需要向量化），对于短文本（场景描述通常只有几个词）效果足够好。向量相似度虽然更准确，但需要额外的嵌入模型调用，增加了路由的延迟和成本。在路由这个场景下，Jaccard 是更合适的权衡。

**认知复杂度层级的设计**：

系统定义了 L1-L4 四个复杂度层级：

- L1：单步、模板化、低幻觉要求（寒暄、格式化、标签分类）
- L2：单步推理、常识、短上下文（客服问答、邮件起草、基础翻译）
- L3：多步推理、代码、分析（代码审查、数据分析、报告生成）
- L4：深度推理、创意、长链思维（架构设计、数学证明、策略规划）

每个提供商配置了它能处理的复杂度层级列表。一个能处理 L4 任务的提供商，当然也能处理 L1-L3 的任务（高层级覆盖低层级）。这个设计确保了路由的合理性：不会把 L4 的复杂任务发给只能处理 L1-L2 的轻量级模型。

#### 4.7.3 熔断器：运行时健康感知

静态路由解决了"任务开始时选谁"的问题，但无法处理"执行过程中提供商突然不可用"的情况。

每个提供商都有一个独立的熔断器（Circuit Breaker），实现三态状态机：

```
CLOSED（正常）
    │ 连续失败次数 ≥ failure_threshold
    ▼
OPEN（熔断，拒绝请求）
    │ 冷却时间到期
    ▼
HALF_OPEN（探测，允许少量请求）
    ├─ 探测成功 → 回到 CLOSED
    └─ 探测失败 → 回到 OPEN（重置冷却）
```

熔断器的核心价值是**快速失败**：当一个提供商已经连续失败多次时，不要再浪费时间等待它的响应，直接切换到备用提供商。这大幅减少了故障期间的等待时间。

**HALF_OPEN 状态的设计**：

当熔断器冷却时间到期后，不是直接回到 CLOSED 状态，而是进入 HALF_OPEN 状态，允许少量探测请求通过。这是因为：提供商可能只是暂时恢复，还不稳定。HALF_OPEN 状态让系统在恢复稳定性之前谨慎地验证提供商是否真的恢复了。

**优先恢复高优先级提供商**：

当当前提供商失败时，系统不是简单地切换到下一个，而是：

1. 先检查是否有**更高优先级的提供商已经从熔断中恢复**（优先回归最优选择）
2. 如果没有，才切换到下一个可用提供商

这个"优先恢复高优先级"的设计，确保系统在故障恢复后能尽快回到最优状态，而不是一直使用次优提供商。

举个例子：假设优先级列表是 [Claude, DeepSeek, Qwen]，Claude 因为过载被熔断，系统切换到 DeepSeek。一段时间后，Claude 的熔断冷却时间到期，进入 HALF_OPEN 状态。下次需要切换提供商时，系统会优先尝试 Claude（因为它优先级更高），而不是继续使用 DeepSeek。

**检查点中的路由状态保存**

熔断器状态会被保存到检查点中。这是一个容易被忽视但很重要的细节。

如果不保存熔断器状态，任务从检查点恢复后，路由器会认为所有提供商都是健康的，可能再次选择之前已经失败的提供商，导致重复失败。保存熔断器状态后，恢复的任务会继承中断前的提供商健康状态，避免这个问题

这里没有深入设计，只做了一些基本的事情

### 5.1 高危工具的安全边界

ThinkingAgent 内置了三个高危工具：`ShellTool`、`RunPythonTool`、`SQLQueryTool`。每个工具都有针对其特定攻击向量的安全设计。

**ShellTool：沙箱隔离**

Shell 工具的主要风险是命令注入和文件系统破坏。

防御措施：

- **工作目录隔离**：所有命令在任务专属的工作目录（`var/runtime/{task_id}/`）中执行，而不是项目根目录或系统目录。即使 LLM 生成了 `rm -rf /` 这样的命令，影响范围也被限制在任务工作目录内。
- **超时限制**：默认 15 秒超时，防止长时间运行的命令阻塞执行流程。
- **非零退出码处理**：命令执行失败（非零退出码）会被转换为结构化错误，而不是静默忽略。

值得注意的是，ShellTool **没有**对命令内容进行白名单过滤。这是一个有意的设计决策：命令过滤很难做到完整，而且会限制工具的灵活性。工作目录隔离提供了足够的安全边界，同时保留了工具的完整功能。

**RunPythonTool：多层沙箱**

Python 工具的风险更复杂：代码执行可以做几乎任何事情，包括访问文件系统、发起网络请求、消耗大量内存等。

防御措施分三层：

第一层，**静态导入检查**：在执行代码之前，用 AST 解析代码，检查所有 `import` 语句。如果发现被禁止的模块（`os`、`subprocess`、`socket` 等），直接拒绝执行，返回错误。

```python
_BLOCKED_IMPORTS = frozenset({
    "os", "sys", "subprocess", "shutil", "socket", "signal",
    "ctypes", "cffi", "multiprocessing", "threading",
    # ...
})
```

第二层，**受限内置函数**：执行代码时，用一个受限的 `__builtins__` 替换标准内置函数，移除了 `open`、`exec`、`eval`、`compile`、`__import__` 等危险函数。同时，`__import__` 被替换为一个守卫版本，在运行时再次检查导入的模块是否在白名单内。

第三层，**子进程隔离 + 资源限制**：代码在独立的子进程中执行（使用 `multiprocessing.Process`），并通过 `resource` 模块设置内存上限（256MB）和 CPU 时间上限（10秒）。即使代码绕过了前两层防御，资源限制也能防止它消耗过多系统资源。

**SQLQueryTool：只读强制**

SQL 工具的风险是 SQL 注入和数据修改。

防御措施：

- **参数化查询**：工具 Schema 明确要求使用参数化查询（`params` 字段），而不是字符串拼接。工具描述中也明确说明"Use placeholders instead of interpolating values directly"。
- **只读限制**：工具描述明确说明只支持 SELECT 语句，后端实现可以在数据库层面强制只读（比如使用只读数据库用户）。
- **行数限制**：默认最多返回 50 行，最大 1000 行，防止全表扫描导致的性能问题。

## 6. 构建飞轮：让 Agent 越用越聪明

### 6.1 两种记忆机制

ThinkingAgent 有两种独立的记忆机制，分别存储不同类型的信息。

**知识库（Knowledge）**：存储关于**世界**的事实性信息。

具体来说，知识库存储的是在任务执行过程中发现的、对未来任务有价值的信息：

- **数据库 Schema**：执行数据分析任务时，LLM 查询了数据库，发现了表结构。这个 Schema 信息对未来的数据分析任务很有价值，可以直接使用，不需要再次查询。
- **API 调用模式**：某个 API 的正确调用方式（参数格式、认证方式、常见错误处理）。
- **数据质量问题**：某个数据源存在的已知问题（比如某个字段有 NULL 值、某些记录的日期格式不一致）。
- **业务规则**：从任务执行中发现的业务规则（比如"VIP 用户的定义是消费金额超过 10000 元"）。

**偏好库（Preference）**：存储关于**用户**的行为偏好。

偏好库存储的是从用户的任务描述和反馈中提取的偏好信息：

- **输出格式偏好**：用户喜欢 Markdown 格式还是纯文本？喜欢详细的分析还是简洁的摘要？
- **语言偏好**：用户习惯用中文还是英文？技术术语用中文还是英文？
- **详细程度偏好**：用户希望看到执行过程的详细日志，还是只看最终结果？
- **工具使用偏好**：用户更喜欢用 Python 处理数据，还是用 SQL？

**两种记忆的使用方式**

知识库在任务开始时被加载，注入到任务上下文中，让 LLM 在推理时可以利用这些已知信息。

偏好库在任务开始时被查询，注入到系统提示中，影响 LLM 的整体行为风格。

### 6.2 异步学习：不影响当前任务

知识提取和偏好提取都是**异步**的——在任务完成后，在后台线程中执行，不阻塞当前任务的返回。

```python
# 任务完成后，异步提取知识和偏好
threading.Thread(
    target=self._knowledge_manager.extract_and_save,
    args=(task, result, self._llm_gateway),
    daemon=True,
).start()
```

**异步的代价**

异步学习意味着：当前任务执行过程中发现的知识，不会在当前任务中被使用。如果任务的第 3 步发现了数据库 Schema，这个信息会在任务完成后才被保存，第 4、5、6 步无法利用这个已保存的知识。

这是一个有意的权衡：**用学习延迟换取执行延迟的降低**。

如果同步提取知识（每个阶段完成后立即提取并保存），每个阶段都会增加一次 LLM 调用的延迟。对于一个 6 步任务，这意味着额外 6 次 LLM 调用，可能增加 30-60 秒的总延迟。

**是否有场景需要同步学习？**

有，但很少见。如果任务的某个阶段发现了关键信息，而后续阶段强烈依赖这个信息，同步学习会更好。

但在实践中，这种情况通常可以通过上下文传递解决：阶段 3 的结果会被放入上下文，阶段 4 可以直接从上下文中读取，不需要经过知识库。知识库的价值在于**跨任务**的信息传递，而不是同一任务内的信息传递。

### 6.3 知识提取的挑战

并不是所有任务执行过程中产生的信息都值得存储。好的知识需要满足几个条件：

**可复用性**：这个信息在未来的任务中会被用到吗？"用户表有 100 万条记录"可能是有价值的（影响查询策略），但"今天的查询返回了 42 条结果"通常没有复用价值。

**稳定性**：这个信息会随时间变化吗？数据库 Schema 相对稳定，值得存储。但"当前活跃用户数"每天都在变化，不适合存储为知识。

**准确性**：这个信息是确定的事实，还是 LLM 的推断？确定的事实（比如从数据库查询到的 Schema）值得存储，但 LLM 的推断（比如"这个字段可能是用户 ID"）不应该作为知识存储。

ThinkingAgent 使用 LLM 来判断哪些信息值得提取为知识。提取提示词明确要求 LLM 只提取"可复用的、稳定的、确定的"信息，过滤掉噪声。

**LLM 提取的局限性**

LLM 提取知识的质量取决于提示词的质量和 LLM 的判断能力。在实践中，LLM 有时会提取过于细节的信息（比如某次查询的具体结果），有时会遗漏重要的信息（比如数据质量问题）。

这是一个需要持续优化的地方。一个可能的改进方向是：让用户在任务完成后审查提取的知识，手动标记哪些值得保留，哪些应该删除。

### 6.4 偏好的衰减与更新

用户偏好会随时间变化。一个用户可能在早期喜欢详细的分析报告，但随着对系统的熟悉，开始偏好简洁的摘要。

**当前的处理方式**

ThinkingAgent 的偏好文件是一个追加写入的 JSONL 文件，每条记录包含 `created_at` 时间戳。当文件超过阈值（64KB）时，自动删除最旧的 20 条记录（`compact()` 方法）。

这是一个简单的"最近优先"策略：较新的偏好记录会保留，较旧的会被删除。这在一定程度上实现了偏好的自然衰减。

**局限性**

当前的实现没有显式的置信度分数或衰减机制。如果用户在 3 个月前表达了某个偏好，这个偏好和昨天表达的偏好在系统中有同等的权重（只要都在文件中）。

**未来改进方向**

1. **置信度分数**：根据偏好被观察到的频率和最近性，计算置信度分数。高置信度的偏好在提示词中占更重要的位置。

2. **显式衰减**：为每条偏好记录设置一个"有效期"，过期的偏好自动降权或删除。

3. **冲突检测**：当新的偏好与旧的偏好冲突时（比如用户之前喜欢详细报告，现在要求简洁），自动识别冲突并更新。

4. **用户反馈循环**：让用户可以显式地确认或否定系统推断的偏好，提高偏好的准确性。

## 8. 结语

- 直接看答案没有意义

  关于如何构建LLM Agent就像这个世界一样，是没有标准答案的。目前为止ThinkingAgent的构建都是基于我的直觉，是把自己想法一股脑倾泻出来的产物。之所以没有上来就参考业界优秀Agent的设计是因为我认为过程比结果重要，每一个设计抉择都是由问题引发的，没有痛过就无法深入理解这个抉择。所以先凭自己感觉手撸一把，再去和优秀的Agent对比学习，我认为是更好的选择，当然这只是我的粗浅之见

- 要让LLM Agent的可靠性设计和基础能力搭建成为量子纠缠现象，从开始就一起去思考可以避免后期对系统架构的剧烈冲击

- 所有的设计都是为了产生一个好的推理轨迹，去控制那台高纬的贝叶斯概率机器

- 做好可观测性，因为调理推理轨迹太依赖这东西。除了数据可能还需要编写必要的辅助分析工具，以及利用LLM一起分析

- 真金白银地测试，应该拿个N+1再走
